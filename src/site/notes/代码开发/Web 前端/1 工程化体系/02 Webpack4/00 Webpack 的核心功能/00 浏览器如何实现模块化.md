当 ES6 带来了模块化后可以方便开发者把一个大型的模块拆分为一个个小的模块然后进行导入组合。

但是这样又会导致一些问题：

1、如果我们把模块拆分的太细又会导致在浏览器中频繁的发送 JS 文件请求，反而降低了页面的访问效率。

2、另外，各大浏览器对 ESModule 的模块化兼容支持也不一致。

3、最后，前端无法使用 npm 的依赖包，因为这些多数都是使用 CommonJS 规范书写的。

当开发一个具有规模的程序，你将遇到非常多的非业务问题，这些问题包括：执行效率、兼容性、代码的可维护性可扩展性、团队协作、测试等等等等，我们将这些问题称之为工程问题。

工程问题与业务无关，但它深刻的影响到开发进度，如果没有一个好的工具解决这些问题，将使得开发进度变得极其缓慢，同时也让开发者陷入技术的泥潭。

这些问题放在 Node 中就会变得微乎其微，因为 Node 执行是在本机执行，不会像浏览器一样来回的进行网络请求，效率上就会比浏览器端高得多。

根本原因还是因为开发时态（devtime）和运行时态（runtime）的侧重点不一样导致的。

开发时态应该：

1. 模块划分越细越好
2. 支持多种模块化标准
3. 支持 npm 或其他包管理器下载的模块
4. 能够解决其他工程化的问题

运行时态应该：

1. 文件越少越好
2. 文件体积越小越好
3. 代码内容越乱越好
4. 所有浏览器都要兼容
5. 能够解决其他运行时的问题，主要是执行效率问题

既然开发时态和运行时态面临的局面有巨大的差异，因此，我们需要有一个工具，这个工具能够让开发者专心的在开发时态写代码，然后利用这个工具将开发时态编写的代码转换为运行时态需要的东西。

这种工具就称为「构建工具」。

这样，开发者只专注于开发业务的功能，不再担心各种工程化问题。

常见的构建工具：

- Webpack，目前最主流
- Gulp
- ...
