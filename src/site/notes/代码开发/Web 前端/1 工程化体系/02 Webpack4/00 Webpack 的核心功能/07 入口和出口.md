## path 模块
在 Node 的环境中，有一个`__dirname`属性，该属性返回的是当前文件在电脑中的绝对路径：

```js
console.log(__dirname)
```

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694164415093-a160da6d-48a8-45e5-8bb2-1c0e1816ebb3.png)

返回 index.js 文件的绝对路径。

Node 的内置模块中有一个 path 模块，该模块是一个对象，对象有一个`reslove()`方法，用于将路径或者路径片段的序列解析为绝对路径，这个函数是跨平台的，也就说能够在 Window、Mac、Linux 上运行。

> 内置模块表示安装 Node 的时候一并安装的依赖模块，不需要使用 npm 单独进行安装。
>

```js
const path = require("path");
console.log(path.resolve("./", "a", "b", "c", "123"));
```

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694164661661-3b9ef35b-e586-438e-8b24-ea762b47005c.png)

可以看到被解析为一个绝对路径。

## 入口
Webpack 的入口配置配置的不是项目的启动文件，而是配置有哪些 chunk，chunk 的名字是什么。

也就是这个部分：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694166264146-7bf90f33-b638-4bab-9d89-5f67f3c5f72e.png)

Webpack 通过`entry`属性来配置入口 chunk，`entry`是一个字符串或对象，如果是字符串但是最终还是会被转换为对象的形式：

```js
module.exports = {
  mode: "development",
  // entry:"./src/index.js"
  // 转换为下面的方式
  entry: {
    main: "./src/index.js"
  }
};
```

在`entry`对象中，key 配置的是 chunk 的名称，value 配置的是 chunk 的入口路径，案例中的配置表示有一个 chunk，chunk 的名称为 main，main 的启动路径为 ./src/index.js 文件，这也就是 Webpack 的默认配置，所以这就是为什么最后输出的结果为 dist/main.js 文件。

例如我们更改这个配置：

```js
const path = require("path");

module.exports = {
    mode: "development",
    entry: {
        // main: "./src/index.js"
        home: "./src/home.js"
    }
};
```

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694166751023-5b6133db-2bf3-4c81-a941-95f80a62827d.png)

最终的编译结果就是 dist/home.js 文件！

某些情况下，chunk 不会只有一个，所以 chunk 可以配置为多个：

```js
module.exports = {
    mode: "development",
    entry: {
        home: "./src/home.js",
        login: "./src/login.js",
        list: "./src/list.js"
    }
};
```

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694166884741-5d8c463c-d81c-4b9c-936a-d7043918abe4.png)

这样就会产生多个 bundle！！！

chunk 还可以配置为多入口，但是最终还是会打包为一个 bundle：

```js
module.exports = {
    mode: "development",
    entry: {
        home: ["./src/home.js", "./src/index.js"],
        login: "./src/login.js",
        list: "./src/list.js"
    }
};
```

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694397126275-88969304-b4a6-4908-a810-c8ee0421d4c8.png)

这样的配置就表示 chunk 为 home 的模块有两个启动模块，分别是 home.js 和 index.js，当配置两个（或者更多）启动模块的时候，home.js 和 index.js 内部应该没有任何的关联。

## 出口
「出口」实际上是用于配置总资源 assets 的文件名或者路径的。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694164851632-a24f3583-c752-4c01-ab8b-dbee5ae4b988.png)

也就是这块的配置。

Webpack 通过`output`属性进行配置，`output`是一个对象：

```js
const path = require("path");

module.exports = {
  mode: "development",
  entry: {
    home: "./src/home.js"
  },
  output: {
    path: path.resolve(__dirname, "target"),
    filename: "js/bundle.js"
  }
};
```

1、`output.path`路径配置

path 必须是一个绝对路径，表示资源要放置的文件夹，默认是`/项目绝对路径/dist`目录。所以我们可以使用`path.resolve()`和`__dirname`属性进行搭配，得到一个绝对路径，最后更改默认的输出位置。

2、`output.filename`文件名称配置

`filename`配置的是资源的文件名，通常有两种写法。

> 前面我们说的`entry`也可以配置`chunk`的名字，但是`output.filename`比`entry`更加的灵活！
>

2.2 静态写法：

适合只有一个入口 chunk 的情况，例如上面的案例我们配置的`output.filename`为 js/bundle.js ，打包结果如下：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694165724663-e005dea2-026a-4a16-97cf-7e0318fc47f1.png)

这个时候 Webpack 就会把名字为 home 的 chunk，打包到 target/js/bundle.js 里面，而不是之前的 dist/main 文件内。

`output.filename`为普通字符串的时候，可以通过 / 来表示具体的文件目录，就像上面中案例一样！

2.2 动态写法：

如果`output.filename`的功能只是如此，那么它就没有存在的必要了。

`output.filename`还支持通过占位符的形式对 bundle 进行命名，例如我们现在配置多个 chunk：

```js
const path = require("path");

module.exports = {
    mode: "development",
    entry: {
        home: "./src/home.js",
        login: "./src/login.js",
        list: "./src/list.js"
    },
    output: {
        path: path.resolve(__dirname, "target"),
        filename: "js/bundle.js"
    }
};
```

如果这个时候再去打包就会产生错误，这是因为 Webpack 输出资源的时候会把所有的 chunk 都名称为 bundle.js 这样就导致重复命名的错误！

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694398239301-b640ced7-b397-4272-86f7-f15ad84da47e.png)

这个时候，我们就不能单纯的把名字设置为一个固定的值，而是使用占位符，占位符可以是如下的内容：

- [name]：根据 chunk 的 name 进行命名。
- [id]：根据 chunk 的 id 进行命名。开发模式时，id 等于 name，生产模式时，id 为从 0 开始的数字。
- [hash:5]：根据总 assets 的 hash 进行命名，且保留 5 位的长度。
- [chunkhash]：根据 chunk 的内容产生的 hash。相比 hash，chunkhash 只会在 chunk 内容发生变化的时候才会改变，不会影响到其他的 chunk，而 hash 是在所有的 chunk 中只要有一个 chunk 的内容发生改变，hash 都会改变。

为什么需要 hash？

hash 主要是为了解决浏览器的缓存问题！

浏览器为了更加高效的网络传输会把第一次请求到的 js 文件缓存到电脑本地，当第二次（或者多次）请求同一个 js 文件的时候，浏览器就会从本地读取这个文件。这样就导致，如果我们服务器上更新了新内容，用户是不能获取到这个新功能的！

所以，我们可以通过 hash 来控制 js 的文件名，如果 chunk 的内容发生了新变化，那么相关的 js 文件都会产生一个新的 hash。这个时候，浏览器看到当前的文件名和上一次的文件名不一样，就会发生请求到服务器获取新的 js 文件，然后把新的 js 文件进行缓存。

<br/>

例如，我们把`output.filename`配置为下面的内容：

```js
const path = require("path");

module.exports = {
  mode: "development",
  entry: {
    home: "./src/home.js",
    login: "./src/login.js",
    list: "./src/list.js"
  },
  output: {
    path: path.resolve(__dirname, "target"),
    filename: "js/[name]-bundle-[chunkhash:5].js"
  }
};
```

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694398929237-61ea094f-fb27-493d-a7a5-bb9fc787c11d.png)

这样，Webpack 就会按照`entry`配置的 name 来对 bundle 进行命名，且后面拼上一个 bundle-5 位哈希值！

## 实践
`entry`和`output`是需要我们根据实际的需求灵活配置的，没有具体的哪种方案。

下面是列举的一些场景：

## 1、一个页面一个 JS
```markdown
|—— src
    |—— pageA   页面A的代码目录
        |—— index.js 页面A的启动模块
        |—— ...
    |—— pageB   页面B的代码目录
        |—— index.js 页面B的启动模块
        |—— ...
    |—— pageC   页面C的代码目录
        |—— main1.js 页面C的启动模块1 例如：主功能
        |—— main2.js 页面C的启动模块2 例如：实现访问统计的额外功能
        |—— ...
    |—— common  公共代码目录
        |—— ...
```

```js
module.exports = {
  entry:{
    pageA: "./src/pageA/index.js",
    pageB: "./src/pageB/index.js",
    pageC: ["./src/pageC/main1.js", "./src/pageC/main2.js"]
  },
  output:{
    filename:"[name].[chunkhash:5].js"
  }
}
```

这种配置适合页面之间功能差异巨大，没有任何联系的情况，但是会存在重复的代码打包。

因为 pageA、pageB、pageC 可能都会依赖 common 目录下的代码，这样就会导致每一个 chunk 都把 common 的代码打包进去！

![画板](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/1%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E4%BD%93%E7%B3%BB/02%20Webpack4/00%20Webpack%20%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD/_assets/1694399588216-994cf5a6-0f19-4ee1-8a18-8452e47c1867.jpeg)

缺点就是，每个 bundle 的体积变大，如果能把 common 单独抽离且每个 bundle 都能自动导入这个文件就好了，这个我们后面学习！

## 2、一个页面多个 JS
```markdown
|—— src
    |—— pageA   页面A的代码目录
        |—— index.js 页面A的启动模块
        |—— ...
    |—— pageB   页面B的代码目录
        |—— index.js 页面B的启动模块
        |—— ...
    |—— init   用于初始化页面的一些内容
        |—— index.js 启动模块
        |—— ...
    |—— common  公共代码目录
        |—— ...
```

```js
module.exports = {
  entry:{
    pageA: "./src/pageA/index.js",
    pageB: "./src/pageB/index.js",
    init: "./src/init/index.js"
  },
  output:{
    filename:"[name].[chunkhash:5].js"
  }
}
```

如果，pageA 和 pageB 没有使用到 init 中的任何代码，init 模块是可以被单独打包的（这里和前面案例不一样，前面案例中 pageA、pageB 和 pageC 都使用了 common 模块的代码）。

因为 init 是对页面进行一些初始化内容，和 pageA、pageB 的页面功能没有联系！

这种方式适用于页面之间有一些独立、相同的功能，专门使用一个 chunk 抽离这部分 JS 有利于浏览器更好的缓存这部分内容。
