## 🔢 使用 script 加载文件
在没有模块化概念之前，都是一个页面引入一个 JS 文件赋负责页面的功能。

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta http-equiv="X-UA-Compatible" content="IE=edge" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Document</title>
  </head>
  <body>
    <script type="text/javascript" src="A.js"></script>
  </body>
</html>
```

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta http-equiv="X-UA-Compatible" content="IE=edge" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Document</title>
  </head>
  <body>
    <script type="text/javascript" src="B.js"></script>
  </body>
</html>
```

如果 A 页面和 B 页面有相同的逻辑，就可以把逻辑单独抽离出去。

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta http-equiv="X-UA-Compatible" content="IE=edge" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Document</title>
  </head>
  <body>
    <script type="text/javascript" src="common.js"></script>
    <script type="text/javascript" src="A.js"></script>
  </body>
</html>
```

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta http-equiv="X-UA-Compatible" content="IE=edge" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Document</title>
  </head>
  <body>
    <script type="text/javascript" src="common.js"></script>
    <script type="text/javascript" src="B.js"></script>
  </body>
</html>
```

但是这样还有问题：

1、如果 common.js 文件中有很多功能的逻辑，而我只想用某一个函数，这样就导致了不合理性。

2、假如 common.js 文件内存在其他 JS 文件的依赖关系，那就必须按照顺序引入。

3、多个 JS 文件的引入会造成变量污染。

```js
var a = function(){ //... }
  var b = function(){
    // 假如 A.js 文件需要依赖这里的 b 函数，在 A.html 页面就必须先引入 common.js 文件再引入 A.js 文件
  }
  // 假如 A.js 文件里也有一个 c 函数，这样 c 函数就会被覆盖
  var c = function(){ //... }
```

所以，模块化的概念就是为了解决以上的问题！

## 🔢 立即执行函数
「立即执行函数」具有立即执行的特性，因为函数有自己的作用域和执行期上下文，可以利用立即执行函数创建模块的独立作用域。

```js
var moduleA = (function(){
  var a = [1, 2, 3, 4, 5].reverse(); // 数组进行反转

  return {
    a
  }
})()
```

```js
var moduleB = (function(moduleA){
  var b = moduleA.a.concat([10, 11, 12])

  return {
    b
  }
})(moduleA)
```

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta http-equiv="X-UA-Compatible" content="IE=edge" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Document</title>
  </head>
  <body>
    <script type="text/javascript" src="module_A.js"></script>
    <script type="text/javascript" src="module_B.js"></script>
    <script type="text/javascript">
      console.log(moduleA.a); // [5, 4, 3, 2, 1]
      console.log(moduleB.b); // [5, 4, 3, 2, 1, 10, 11, 12]
    </script>
  </body>
</html>
```

这样虽然解决了变量污染的问题，但是依然必须按照顺序来加载文件。

## 🔢 CommonJS
JavaScript 真正实现模块化是在基于谷歌 V8 引擎运行的 NodeJS 出现之后。从此，JS 第一次堂堂正正的入驻后端，不再是必须附属于浏览器的“玩具”语言了。

也是从此刻开始，人们认识到，JS（ES）是一门真正的语言，它依附于运行环境（运行时）（宿主程序）而执行。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/02%20JavaScript/02%20ECMAScript6+/_assets/1692516286012-03ae3f8a-7810-4835-aafb-393beb1c16ef.png)

NodeJS 是后端服务语言，如果不解决全局变量污染和依赖混乱问题，那么就无法实现模块化的开发，无法开发大型的项目。

经过社区的激烈讨论，最终，形成了一个模块化方案，即鼎鼎大名的 CommonJS 规范，该方案，彻底解决了全局变量污染和依赖混乱的问题。

<br/>tips
CommonJS 是一种模块化的规范而不是任何的 JS 代码，其来源于 NodeJS，所以 CommonJS 只能运行在 NodeJS 中。

<br/>

该方案一出，立即被 NodeJS 支持。于是，NodeJS 成为了第一个为 JS 语言实现模块化的平台，为前端接下来的迅猛发展奠定了实践基础。

在 NodeJS 中，由于有且仅有一个入口文件（启动文件），而开发一个应用肯定会涉及到多个文件配合，因此，NodeJS 对模块化的需求比浏览器端要大的多。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/02%20JavaScript/02%20ECMAScript6+/_assets/1692516509019-c057a35c-1a5c-4afa-91de-5d1568f7176c.png)

CommonJS 有两个很重要的概念，那就是模块的「导出」和「导入」。

什么是模块？

模块就是一个 JS 文件，它实现了一部分功能，并隐藏自己的内部实现，同时提供了一些接口供其他模块使用。

```js
var count = 0;

function getNumber(){
  return count++;
}
```

比方说，`getNumber()`函数就是希望外部可以调用的，`count`属性是不希望外部能访问的。

任何一个正常的模块化标准，都应该默认隐藏模块中的所有实现，而通过一些语法或 API 调用来暴露接口

暴露接口的过程即模块的导出。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/02%20JavaScript/02%20ECMAScript6+/_assets/1723708917682-559d3e51-670e-4143-a6a7-61d3cbe9a5d8.png)

当需要使用一个模块时，使用的是该模块暴露的部分（导出的部分），隐藏的部分是永远无法使用的。

当通过某种语法或 API 去使用一个模块时，这个过程叫做模块的导入。

## 🔢 > 导出 & 导入
CommonJS 规范使用`exports`导出模块，`require`导入模块。

具体如下：

1、如果一个 JS 文件中存在`export`或者`require`，则认为 JS 文件是一个模块。

2、模块内所有的代码均为隐藏代码，包括全局变量、全局函数，这些全局的内容都不应该对全局变量造成污染。

3、如果一个模块需要暴露出一些 API 提供给外部使用，需要使用`exports`导出，`exports`是一个空对象，你可以为该对象添加任何需要导出的内容。

4、如果一个模块需要导入其他模块，通过`require`实现，`require`是一个函数，传入模块的路径即可返回该模块导出的整个内容。

```js
// 不会污染外部的全局变量
var count = 0;

function getNumber(){
  return count++;
}

// 导出内容
exports.getNumber = getNumber;

/*
  等同于：
  exports: {
    getNumber: getNumber
  }
*/
```

```js
// 导入模块
const utils = require("./utils.js");

/*
  utils 内容如下：
  {
    getNumber: getNumber
  }
*/

// 不会和 utils.js 文件内的 count 产生冲突
var count = 100;

console.log(utils.getNumber());
console.log(utils.getNumber());
// 无法访问 utils 内的 count 变量
console.log(utils.count);
```

## 🔢 > NodeJS 对 CommonJS 的实现
1、为了保证高效的执行，仅加载必要的模块。NodeJS 只有执行到`require()`函数时才会加载并执行模块。

相当于是运行到`require()`的时候查看路径是否存在，如果能找到则把模块内的代码执行一遍，并把`exports`的内容作为返回值返回。

<br/>

在 NodeJS 中如果要导入模块，需要使用相对路径使用`./`或者`../`进行查找，如果不加则表示查找node_modules 和内置模块。

<br/>

```js
console.log("This is index.js file.");

const utils = require("./utils");

console.log(utils);
```

```js
console.log("This is utils.js file.");

let count = 0;

function add() {
  return count++;
}

module.exports = {
  add
};
```

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/02%20JavaScript/02%20ECMAScript6+/_assets/1692516983890-72fbae5a-e1f3-4aba-a84a-ca8eeff136bb.png)

2. 为了隐藏模块中的代码，NodeJS 执行模块时，会将模块中的所有代码放置到一个函数中执行，以保证不污染全局变量。

```js
// 类似这样，但内部不是这样实现的！
(function(){
  // 模块中的代码
})()
```

3. 在模块开始执行前，初始化一个值`module.exports = {}`，`module.exports`即模块的导出值。

```js
(function(module){
  module.exports = {};
  // 模块代码
  return module.exports;
})()
```

4. 为了方便开发者便捷的导出，NodeJS 在初始化完`module.exports`后，又声明了一个变量`exports = module.exports`进行了引用。

```js
(function(module){
  module.exports = {};
  var exports = module.exports;
  //模块中的代码
  return module.exports;
})()
```

所以，我们在写模块的时候千万不能把`exports`复制为一个新对象，因为这样会导致`exports`和`module.exports`的引用关系丢失！而是通过`exports.xxx=xxx`这样的方式赋值。同样的道理，当我们重新给`module.exports={}`的时候，`exports`都将无效了。

```js
console.log("This is utils.js file.");

let count = 0;

function add() {
  return count++;
}

exports.minus = function () {
  return count--;
};

module.exports = {
  add
};

```

5. 为了避免反复加载同一个模块，NodeJS 默认开启了模块缓存，如果加载的模块已经被加载过了，则会自动使用之前的导出结果。

```js
console.log("This is index.js file.");

const utils = require("./utils");

console.log(utils.add());
console.log(utils.add());

require("./index2")
```

```js

const utils = require("./utils")

console.log(utils.add())
console.log(utils.add())
console.log(utils.add())
```

可以看到，当 index.js 文件加载完 utils.js 文件后，utils 文件会执行一次，当 index2.js 文件再导入 utils.js 的时候，utils.js 却没有再执行而是使用之前的缓存结果！

## 🔢 > 同步加载

`CommonJS`只要引入就会创建一个模块的实例（实例化）

所有的文件都是同步进行加载的，这是因为`commonJS`运行在服务端（也就是本地）所以加载模块特别的快，也就没有必要使用异步加载！

<br/>

```js
var moduleA = (function(){
  var a = [1, 2, 3, 4, 5].reverse();

  return {
    a
  }
})();

module.exports = {
  moduleA
}
```

```js
var moduleA = require("./module_A.js")

var moduleB = (function(){
  var b = moduleA.a.concat([10, 11, 12])

  return {
    b
  }
})();
```

## 🔢 浏览器模块化的难题
按道理说，既然 NodeJS 实现了 CommonJS 的模块化规范，前端直接拿过来用不就可以了吗？

可是 CommonJS 加载模块的时候是「同步加载」的，当文件加载完成后再执行后面的代码。NodeJS 运行在服务端，加载模块都是在本机寻找文件整个过程会非常的快。

而到了浏览器中，浏览器要加载一个 JS 文件都是需要从远端服务器中读取，而网络传输的效率远远低于node 环境中读取本地文件的效率。如果浏览器也使用 CommonJS 那么就会造成加载模块的时候，网络慢造成页面卡死的情况出现。

![画板](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/02%20JavaScript/02%20ECMAScript6+/_assets/1723773977953-6ed47086-b9f2-4553-bb40-ced1db0db5b9.jpeg)

基于这个原因，浏览器无法使用 CommonJS 的规范。如果能把加载 JS 文件做出异步的模式就好了，并且具有导入导出的功能。基于这种思路出现了 AMD 和 CMD，有效的解决了浏览器模块化的问题。

## 🔢 AMD
AMD，全称是 Asynchronous Module Definition，即异步模块加载机制，主要依赖于`require.js`文件，导入和导出摸的代码，都必须放在`define()`函数中。

AMD 推崇「依赖前置」，也就是说：依赖必须一开始就写好，会先尽早地执行（依赖）模块 。换句话说，所有的`require`都被提前执行（`require`可以是全局或局部 ）。

基本语法：

```js
define([依赖的模块列表], function(模块名称列表){
  //模块内部的代码
  return 导出的内容
})
```

示例：

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <title></title>
  </head>
  <body>
    <!-- 引入 require.js，然后使用 data-main 属性指定入口文件为 main.js -->
    <script data-main="main" src="require.js"></script>
  </body>
</html>
```

```js
console.log("index.js");

// 当加载完成 require.js 文件后，define 函数就是一个全局的函数
// a 模块的路径是相对于入口文件的路径
define(["a"], function (a) {
  // 当 a.js 文件加载完成后再运行该函数
  // 也解决了污染全局变量的问题
  console.log(a);
});
```

```js
// define 的第一个参数如果不是数组
// 那就表示要导出的模块，函数的返回值就是导出的值
define(function () {
  var name = "ModuleA";

  return {
    name
  };
});
```

AMD 基本原理还是动态的加载`<script>`文件：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/02%20JavaScript/02%20ECMAScript6+/_assets/1692693438646-5a50f800-1a57-4121-8e33-9ced822afb98.png)

AMD 还实现了类似 CommonJS 语法的写法：

```js
define(function(require, exports, module){
  const util = require("./util");
  // 模块代码
  module.exports = 导出的内容;
}
```

手动实现一个简单的`require.js`:

```js
let namespace = (function () {
  let cache = {};

  // 返回一个闭包，实现属性私有化
  // name定义模块的名称 deps模块的依赖 fn的实现方式
  return function createdModule(name, deps, fn) {
    deps = deps.map((depName) => {
      return cache[depName];
    });

    cache[name] = fn.apply(null, deps);
    return cache[name];
  };
})();

// 定义模块名称，所依赖的模块，模块的实现方式
namespace("math", [], function () {
  function add(a, b) {
    return a + b;
  }
  function sub(a, b) {
    return a - b;
  }

  return {
    add,
    sub,
  };
});

// 有一个模块就有一个参数
namespace("calculator", ["math"], function (math) {
  var action = "add";

  function computed(a, b) {
    math[action](a, b);
  }

  return {
    computed,
  };
});
```

## 🔢 CMD
CMD 全称是 Common Module Definition，即公共模块定义规范，主要依靠的是 sea.js 文件。

它推崇「依赖就近」，想什么时候`require`就什么时候加载，实现了懒加载（延迟执行 ） ；

<br/>tips
最开始的时候 AMD 的 require.js 并没有实现类似 CommonJS 的写法，后来 CMD 的热度上升 require.js 也支持了类似 CommonJS 的写法。所以，AMD 支持多种写法。

<br/>

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta http-equiv="X-UA-Compatible" content="IE=edge" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Document</title>
  </head>
  <body>
    <script type="text/javascript" src="sea.js"></script>
    <script type="text/javascript">
      // 指定入口文件
      seajs.use('./scripts/main');
    </script>
  </body>
</html>
```

```js
define(function(require, exports, module) {
  /* 按需加载 a.js */
  var a = require('./a');
  console.log(a.getTime());
});
```

```js
define(function(require, exports, module) {
  exports.getTime = function() {
    return new Date();
  }
});
```

AMD 与 CMD 的比较：

AMD：依赖前置，预执行（异步加载，依赖先执行）。

CMD：依赖就近，懒执行（运行到需加载，根据顺序执行）。

## 🔢 ESModule
AMD 和 CMD 都是民间创建的用法，直到 ES6 的发版带来了 ESModule 模块化，是目前主流的模块化规范，相当于把 AMD 和 CMD 进行了整合。

ES6 模块化具有以下的特点：

1. 使用「依赖预声明」的方式导入模块；

「依赖预声明」和「依赖延迟声明」对比：

1. 依赖延迟声明（例如 CommonJS 的`require()`）；
    1. 优点：某些时候可以提高效率；
    2. 缺点：无法在一开始确定模块依赖关系（相对比较模糊）；
2. 依赖预声明；
    1. 优点：在一开始可以确定模块依赖关系；
    2. 缺点：某些时候效率较低；

<br/>

2. 灵活的多种导入导出方式；
3. 规范的路径表示法：所有路径必须以`./`或`../`开头；

为了区分和普通的`<script>`脚本文件，ESModule 规定带有`type="module"`属性的`<script>`标签会告诉浏览器相关代码应该作为模块执行，而不是作为传统的脚本执行。

模块可以嵌入在网页中， 也可以作为外部文件引入：

```html
<script type="module">
	// 模块代码
</script>

<script type="module" src="./main.js"></script>
```

所有模块都会像`<script defer>`加载的脚本一样按顺序执行。解析到`<script type="module">`标签后会立即下载模块文件，但执行会延迟到文档解析完成。

<br/>warning
⚠️ 注意

`type="module"`只能运行在 http/https 的服务下，如果你直接在本地打开 html 文件将会收到跨域的报错信息！

<br/>

 使用`<script type="module">`的脚本文件不会污染全局变量：

```html
<script type="module" src="./index.js"></script>
<script>
  // a is not defind
  console.log(a);
</script>
```

```js
// 模块内的代码不会污染全局变量
var a = 1;
```

ES6 模块支持两种导出：命名导出和默认导出。不同的导出方式对应不同的导入方式。

## 🔢 > 基本导出
基本导出类似于 CommonJS 中的`export.xx = xx`，基本导出可以有多个，每个必须有名称。

```js
export 声明表达式;

// 或者

export {具名符号};
```

导出声明表达式的案例：

```js
// 导出 str，值为 'abc'
export var str = 'abc';

// 导出 sum，值为一个 Function
export function sum(num1, num2){
  return num1 + num2;
}
```

导出具名符号案例：

```js
var str = 'abc';

function sum(num1, num2){
  return num1 + num2;
}

// 表示将 str 变量的名称作为导出的名称，str 变量的值作为导出的值
export {
  str,
  sum
}
```

<br/>warning
⚠️ 注意

`export {}`不是对象！！！

`export { str: 'abc' }`这样写会导致错误。

<br/>

使用具名符号的方式导出时，可以进行重命名：

```js
var a = 100;

export { a as str };
```

## 🔢 > 基本导入
对于基本导出可以使用基本导入。由于使用的是「依赖预加载」，因此导入任何其他模块，导入语句都必须放在所有代码之前。

```js
import { 导入的符号列表 } from "模块路径";

// ...其他的业务代码
```

基本导入案例：

```js
import { str, sum } from "./demo.js";

// ...其他的业务代码
```

导入细节：

1、导入时，可以通过关键字`as`对导入的符号进行重命名。

```js
import { str as letterStr , sum } from "./demo.js";
```

2、导入时，使用的符号是常量，不可以修改。

```js
import { str , sum } from "./demo.js";

str = 'bcd'; // ❌Error
```

3、导入时，可以使用`*`号导入并进行重命名所有的基本导入，形成一个对象。

```js
import * as demo from "./demo.js";

demo.sum(10, 20);
```

## 🔢 > 默认导出
每个模块，除了允许有多个基本导出之外，还允许有一个默认导出（可以同时存在）。

默认导出类似于 CommonJS 中的`module.exports`，由于只能有一个，因为不需要具名。

```js
export default 默认导出的数据;

// 或者

export { 默认导出的数据 as default };
```

默认导出案例：

```js
export var str = 'abc'; // 基本导出

export default 200; // 默认导出
```

```js
var num = 200;

export var str = 'abc'; // 基本导出
export { num as default }; // 默认导出
```

## 🔢 > 默认导入
如果要实现一个模块的默认导入，需要使用下面的语法：

```js
import 接收变量名 from "模块路径";
```

默认导入案例：

```js
import demo from "./demo.js"; // 将 demo.js 模块中的「默认导出」放到常量 demo 中去
```

如果希望同时导入某个模块的默认导出和基本导出，可以使用下面的语法：

```js
import 接收默认导出的变量, { 接收基本导出的变量 } from "模块路径"
```

```js
import demo, { str, sum } from "./demo.js";
```

或者对`default`关键字进行重命名：

```js
import { str, sum, default as demo } from "./demo.js";
```

也可以使用使用`*`号，将所有基本导出和默认导出聚合到一个对象中，默认导出会作为属性`default`存在：

```js
import * as demo from "./demo.js";

/*
  demo 值如下：
  {
    str: 'abc',
    sum: function,
    default: 200
  }
*/
```

## 🔢 > 其他细节
1、尽量导出不可变值。

当导出一个内容时，尽量保证该内容是不可变的。

虽然导入后，无法更改导入内容，但是在导入的模块内部却有可能发生更改，这将导致一些无法预料的事情发生。

```js
export let name = "模块a";

export default function(){
  name = "module a";
}
```

```js
import method, { name } from "./a.js";

console.log(name); // 模块a

method();

console.log(name); // module a
```

2、如果不需要模块的导出，但仍想加载和执行模块，可以只通过路径加载它。

```js
import './foo.js';
```

只是执行一次 foo.js 文件内的代码，但是不会使用内部任何的内容。

3、如果想把一个模块的所有命名导出集中在一块，可以像下面这样在`bar.js`中使用`*`导出：

```js
// foo.js
export let name = 'abc';

// bar.js
export let age = 30;

// index.js
export { name } from './foo.js';
export * from './bar.js';
```

## 🔢 > import()
`import`命令会被`JavaScript`引擎静态分析，先于模块内的其他语句执行。所以，下面的代码会报错。

```js
// 报错
if (x === 2) {
  import MyModual from './myModual';
}
```

如果`import`命令要取代`Node`的`require`方法，这就形成了一个障碍。因为`require`是运行时加载模块，`import`命令无法取代`require`的动态加载功能。

```js
const path = './' + fileName;
const myModual = require(path);
```

所以在`ES2020`的时候提出了`import()`来动态加载模块，该方法返回一个`Promise`：

```js
const someVariable = "test";

import(`./section-modules/${someVariable}.js`)
  .then(module => {
    // ...
  })
  .catch(err => {
    // ...
  });
```

`import()`它是运行时执行，也就是说，什么时候运行到这一句，就会加载指定的模块。另外，`import()`函数与所加载的模块没有静态连接关系，这点也是与`import`语句不相同。`import()`类似于`Node.js`的`require()`方法，区别主要是前者是异步加载，后者是同步加载。

## 🔢 CJS 和 ESM 的区别
- 两者的模块导入导出语法不同，CommonJS 是通过`module.exports`或`exports`导出，`require`导入。ESModule 则是`export`导出，`import`导入;
- CommonJS 是运行时加载模块，ESModule 是在静态编译期间就确定模块的依赖;
- ESModule 在编译期间会将所有`import`提升到顶部，CommonJS 不会提升`require()`;
- CommonJS 导出的是一个值拷贝，会对加载结果进行缓存，一旦内部再修改这个值，则不会同步到外部。ESModule 是导出的一个引用，内部修改可以同步到外部;
- CommonJS 中顶层的`this`指向这个模块本身，而 ESModule 中顶层`this`指向`undefined`;
- CommonJS 加载的是整个模块，将所有的接口全部加载进来，ESModule 可以单独加载其中的某个接口；

> [!tip]
> Tree-Shaking 就是通过 ES6 Module 的`import`来进行静态分析，并且只支持 ES6 Module 模块的使用。Tree-Shaking 就是移除掉 JS 上下文中没有引用的代码，比如当导入的模块没有被实际使用时，Webpack 在打包编译过程中会通过 Tree-Shaking 自动忽略这些未被引用的模块。
