HTTP 协议经历了几个版本，每个版本都对相关的问题进行了优化。

## 🔢 HTTP 0.9
该版本是 HTTP 最初的协议版本，只包含一些简单的功能：

1. 仅支持 GET 请求方式。
2. 无请求头和响应头。
3. 无状态码。
4. 仅能请求访问 HTML 格式的资源。

## 🔢 HTTP 1.0
新增内容：

1. 新增 POST 和 HEAD 请求方式。
2. 支持请求头和响应头。
3. 新增状态码、多字符集支持、内容编码等。
4. 支持客户端缓存控制（`Expires`、`Last-Modified`）。
5. 支持图片、脚本等非 HTML 内容。

局限性：

1. 单次 TCP 连接，每个请求完成后立即关闭 TCP 连接（缺乏持久化连接）。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740713535905-903c228c-90b2-4b51-a855-1a3efb88b585.png)

这个版本存在最大问题就是必须等之前的请求响应完成后，才能进行下一次的请求。

## 🔢 HTTP 1.1
这个版本也是最广泛使用的版本。

1. 增加 PUT、PATCH、OPTION、DELETE 等请求方式。
2. 更丰富的缓存控制（`Cache-Control`, `ETag`），客户端可以更高效地缓存资源。
3. 支持数据的分块传输（例如文件断点续传）。
4. 默认开启 Connection: keep-alive 持久化连接，允许多个请求复用一个 TCP 连接。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740714692896-16dc2ce6-6311-4b4c-a1ad-9683ba97fb4d.png)

这种情况就可以实现多个请求共用一个 TCP 连接，减少了握手和挥手的时间。

如何关闭长连接呢？

- 客户端某一次请求头设置`Connection: close`，服务器收到这个请求后，在响应完成后立即关闭 TCP；
- 在没有请求时，客户端会不断对服务器进行心跳检测（一般每隔 1 秒）。一旦心跳检测停止，服务器立即关闭 TCP；

5. 新增管道化机制，支持多个请求同时发送。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740721778317-d1d8874d-6431-42c5-848d-c90e15247bbd.png)

允许之前某个请求未响应之前发送下一个请求，但是必须等待之前的请求响应后才能响应下一个请求。这么做的目的是为了保持正确的顺序，例如 A 问你 10 个问题，你随机进行回复，A 怎么知道你回复的是哪个问题呢？所以，这个版本的还不算彻底解决「队头阻塞」的问题。

要优化这个问题，浏览器会在请求大量资源的时候会开启多个 TCP 通道，让请求分散在不同的 TCP 里，尽量减少队头阻塞。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740722064917-2f3f93ae-673d-4303-b70d-cdb09f153e43.png)

最后，管道化传输并不是一个成功的模型，它带来了队头阻塞非常多的问题，所以现代浏览器默认是关闭这种模式的。

## 🔢 HTTP 2.0
1、二进制协议。

这个版本可以允许以更小的单元传输数据，每个传输单元被称为「帧」，而每一个请求或响应完整数据被称为流，每个流都有自己的编号，每个帧会记录所属的流。

例如服务器连续接收到客户端两个请求，分别是 JS 和 CSS：

```js
function a(){}
function b(){}
```

```css
.container{}
.list{}
```

最后形成的帧可能如下：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740722972232-60960687-06b1-4189-a044-b2850b8cc864.png)

可以看出，每一个帧都带了一个头部，里面记录了流的 ID，这样做能够准确的知道这一帧是属于哪个流的。

这样就真正解决了公用 TCP 连接时候的队头阻塞问题，实现了真正的「多路复用」。也就是在进行传递数据的时候就可以乱序交替传输了，因为有流的 ID 作为标识（同一个流内的帧不能乱序）。

Tip

HTTP 1.1 的传输单元是整个响应文本，因此接收方必须按序接收完所有的内容后才能接收下一个传输单元，否则就会造成混乱。

<br/>

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740723464442-11b2b9ec-6cee-4f83-9fb2-c747016e2203.png)

2、请求头压缩。

这个版本还使用 HPACK 算法压缩请求头，减少了请求头的大小，降低了带宽的消耗。

具体做法如下：

静态表和动态表两个表里记录了 HTTP 请求头信息，并分配了固定的编号。当客户端发送 HTTP 请求的时候会查询一下静态表，将表中记录的字段替换为对应的编号，如果静态表中没有某个字段，则不能替换为变化，需要原封不动的发送到服务端，并且会记录到动态表中。

当服务器接收到 HTTP 头信息的时候，也会到静态表中进行替换为具体的字段信息，如果静态表中没有，则会到动态表中进行查找和记录。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740725145175-74bc1710-0a36-4c5f-9a94-b669ab67a88f.png)

Tip

带有`:`的头字段是伪头部字段，是 HTTP 2.0 为了进行优化传输，将请求行中信息抽离到了请求头中。

<br/>

```plain
GET / HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept-Encoding: gzip, deflate
Auth: token=xxx

HTTP 2.0
:method: GET
:path: /index.html
:scheme: https
User-Agent: Mozilla/5.0
Accept-Encoding: gzip, deflate
Auth: token=xxx
```

3、服务器推送。

允许服务器在客户端请求之前主动推送资源，减少了加载时间。

## 🔢 HTTP 3.0
目前（2024 年）HTTP 3.0 的协议在 2021 年 6 月被正式标准化，但是目前来看还没有大量的普及，仍然有一部分设备不支持这个版本。

1、基于 QUIC（Quick UDP Internet Connections）协议构建，采用 UDP 协议，抛弃了 TCP 协议。

2、多路复用改进。

在 HTTP 2.0 中，虽然可以多路复用请求，但如果一个流发生丢包，整个连接的传输都会受到影响。HTTP 3.0 通过 QUIC 的多路复用特性，避免了这个问题。

3、QUIC 本身支持 TLS（传输层安全协议），因此 HTTP 3.0 默认启用了加密;
