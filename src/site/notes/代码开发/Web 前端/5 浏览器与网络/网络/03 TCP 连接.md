TCP 协议的全称是传输控制协议（Transmission Control Protocol）。

- TCP 是面向连接的，为了方便传输，TCP 协议会把将大块数据分割成以报文段为单位的数据包进行管理。而可靠的传输服务是指，能够把数据准确可靠地传给对方，也就是说必须进行连接的过程才能进行通信。
- TCP 与 HTTP 协议不同，TCP 不要求客户端发送请求再等待服务器的响应，数据的发送和接收可以是双向的，且不一定总是由客户端发起请求，服务器也可以主动向客户端发送数据。
- 而且数据传输时间不固定，TCP 允许在长时间内保持连接，因此数据可以在几分钟、几小时，甚至几天内通过 TCP 连接传输。这个时间跨度通常取决于应用场景和数据的大小。例如，长时间保持连接进行数据流传输（如视频流、文件传输等）时，TCP 会保持会话的开放状态，直到所有数据完成传输。

## 🔢 TCP 如何收发数据
1、分段传输。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740661483391-da23dbcc-75f9-48d0-aac4-c3a5595d4105.png)

TCP 在进行收发数据的时候会将完整的数据拆分为多个段，发送数据的时候是一个段一个段的发送。每个数据段 + 一个头部信息组合成一个数据报。头部信息中包含序列号、确认号等信息，这个序列号用于保证数据能够按照顺序到达接收方。

<br/>tips
Info

一个完整的数据报 = 头部信息 + 载荷。

载荷则是实际传输的数据，可能包含来自应用层的数据，比如 HTTP 报文。

<br/>

2、可靠的传输。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740662008662-e5a008f9-df61-496f-9f7f-37d1503d6d58.png)

开头的时候就提到了，TCP 的数据发送是双向的，任何一方都可以主动给对方发送数据。

当一个完整的数据被拆分为多个数据报的时候，就会开始进行传输。为了解决数据报丢失、数据报错乱等问题，TCP 的协议要求：接收方收到数据之后，必须对数据报进行确认。

<br/>tips
Info

SYN、ACK 都只是一种标志位，都属于数据报头 Flags 的一部分：

- SYN (Synchronize)：用于初始化连接，表示客户端或服务器希望开始建立连接；
- ACK (Acknowledgment)：表示确认收到某个数据包；
- FIN (Finish)：表示请求断开连接；
- RST (Reset)：表示重置连接；
- URG (Urgent)：表示该数据包包含紧急数据；

<br/>

例如：

```plain
服务器 → 客户端:
SYN-ACK
- Sequence number: 2000
- Acknowledgment number: 1001
- Flags: SYN = 1, ACK = 1
```

如果发送方长时间没有收到接收方的确认数据报（ACK=1），那么则会判定之前的数据报丢失或者错误，然后会重新发送之前的数据报。

## 🔢 建立连接（三次握手）
TCP 协议要实现数据的收发，首先要建立连接，两方都可以主动发起。

连接本质上就是双方各自开辟的一块内存空间，空间中主要是进行数据缓冲区和一些变量。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740646766990-76fe4bd1-fac2-4bd1-9b14-73cb05e9a052.png)

连接建立的过程需要经过三次数据报的传输，因此被称为三次握手。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740663556077-64b95447-2e4b-4a5c-ae8c-cc54b82e1833.png)

1. 初始状态：双方都处于 CLOSE（关闭）状态，表示连接未建立，等待建立连接的请求。
2. <u>客户端发起连接请求：</u>
    - 客户端主动向服务端发送一个 SYN（同步）标志位的数据包，表示希望建立连接，客户端进入 SYN_SEND（等待服务端确认）状态。
    - 头信息：
        * SYN：表示请求同步，表示客户端希望与服务端建立连接（SYN 包本身不携带数据，仅用于同步建立连接）。
        * seq：初始化的序列号，标识客户端发送的字节流的起始位置。
3. <u>服务端响应客户端请求：</u>
    - 服务端收到客户端的 SYN 请求后，返回一个带有 SYN+ACK 标志位的数据包，表示服务端收到客户端的连接请求，并同意建立连接，服务端进入 SYN_RECV（收到请求并确认）状态。
    - 头信息：
        * SYN：表示同步请求，服务端同意建立连接。
        * seq：服务端初始化的序列号，用于标识服务端发送的字节流的起始位置。
        * ACK：确认客户端的请求，表示服务端已经收到客户端的 SYN 包，并希望下次客户端发送的数据包序列号 +1。
        * ack：确认客户端的 seq 序列号 +1，表示服务端已收到客户端的同步请求。
4. <u>客户端确认连接建立：</u>
    - 客户端收到服务端的 SYN+ACK 数据包后，向服务端再次发送一个 ACK（确认）标志位的数据包，表示客户端最终确认连接建立。客户端进入 ESTABLISHED（建立连接）状态。
    - 头信息：
        * ACK：确认请求，表示客户端确认收到服务端的 SYN+ACK 数据包。
        * seq：客户端发送的序列号，用于标识客户端发送的字节流的起始位置。
        * ack：确认服务端的序列号 +1，表示客户端已收到服务端的确认。
5. 服务端确认连接建立：
    - 服务端收到客户端的 ACK 确认包后，服务端也进入 ESTABLISHED（建立连接）状态，表示连接建立完成，双方可以开始数据传输。

通俗一点说：

客户端：喂？服务端我是客户端你能听到吗？

服务端：我能听到，你能听到我说话吗？

客户端：可以听到，那我们互相都能听到对方的话，我们的通信可以开始了。

TCP 建立完成之后就可以进行数据的传递了。

## 🔢 连接的销毁（四次挥手）
当客户端和服务端之间的数据传输完毕后，就可以关闭 TCP 连接。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740707167555-d108f75b-a097-46f0-9a6e-e073c2c4437b.png)

1. 初始状态：双方都处于连接状态，可以进行数据传输。
2. <u>客户端发起断开请求：</u>
    - 客户端主动向服务端发送一个带有 FIN（请求断开连接）标志位的数据包，表示客户端请求关闭连接。客户端进入 FIN-WAIT-1（等待中断）状态。
    - 头信息：
        * FIN：表示请求断开连接的标志位。
        * seq：初始化的序列号，用于标识客户端发送的字节流序列。
3. <u>服务端确认收到断开请求：</u>
    - 服务端收到客户端的断开连接请求后，返回一个带有 ACK（确认）标志位的数据包，表示确认收到客户端的断开请求。服务端进入 CLOSE-WAIT（关闭连接等待）状态。
    - 头信息：
        * seq：服务端生成的初始化序列号。
        * ACK：确认客户端请求的标志位。
        * ack：确认客户端请求的序列号 + 1，表示下一个期望收到的数据的序列号。
4. 服务端准备关闭连接：
    - 由于服务端可能还有数据未发送完，因此在此时会进行半关闭状态，客户端仍可以接收数据。
5. <u>服务端发送 FIN+ACK 数据包：</u>
    - 当服务端数据发送完毕后，服务端主动发送带有 FIN（请求断开连接）和 ACK（确认）标志位的数据包，表示请求关闭连接，并进入 LAST-WAIT（最后等待）状态。
    - 头信息：
        * FIN：表示请求断开连接的标志位。
        * seq：服务端生成的初始化序列号，用于标识服务端发送的字节流序列。
        * ACK：确认客户端请求的标志位。
        * ack：确认客户端的序列号 + 1，表示希望客户端下次发送的序列号。
6. <u>客户端确认断开请求：</u>
    - 客户端收到服务端的 FIN+ACK 数据包后，发送一个 ACK（确认）数据包，确认服务端的断开请求。客户端进入 TIME-WAIT（时间等待）状态。
    - 头信息：
        * ACK：表示确认服务端请求的标志位。
        * ack：确认服务端的序列号 + 1，表示希望下次接收到服务端发送的数据的序列号。
        * seq：客户端发送的序列号，用于标识客户端发送的字节流序列。
7. 服务端关闭连接：
    - 服务端收到客户端的最后确认包后，立即进入 CLOSE（关闭）状态，表示连接完全关闭。
8. 客户端在发送完最后一个 ACK 包后，会保持 TIME-WAIT 状态，等待 2MSL（最大段生存时间）后，确保服务端已收到确认包，然后进入 CLOSE 状态。
9. TCP 连接关闭：
    - 在客户端进入 CLOSE 状态后，TCP 连接最终关闭。

通俗一点说：

客户端：我所有东西都说完了。

服务端：我已经全部听到了，但是等等我，我还没说完。

服务端：好了，我已经说完了。

客户端：好的，那我们的通信结束。

Tip

2MSL 表示最大报文生存时间，目的防止数据在传输的过程中失败。假如客户端给服务端发送的最后一个 ACK 数据包丢失了，这个时候客户端立即进入了 CLOSE 状态，但是服务端没有收到这个包，就导致服务端的 TCP 一直不能关闭。服务端就会重新发送一次 ACK+SYN 的请求，但是客户端已经关闭了，导致服务端不停的重新发送 ACK + SYN，服务器的内存也就一直不能释放。

## 🔢 HTTP 和 TCP 的关闭
![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E7%BD%91%E7%BB%9C/_assets/1740710584038-8f8f244c-3e21-4f58-b0f7-60d8f92cbb95.png)

HTTP 协议是对内容格式的规定，它使用了 TCP 协议完成消息的可靠传输。

在具体使用 TCP 协议的时候：

1、客户端发消息给服务器叫做请求，服务端给客户端返回数据叫做响应；

2、使用 HTTP 协议的服务器不会主动发信息给客户端，只会对请求进行响应；

3、每一个 HTTP 请求+响应，都要进行建立 TCP 连接（三次握手），然后完成响应后再销毁 TCP 连接（四次挥手）。这就导致每次请求+响应都是独立的，无法保持状态；

```latex
Ajax ==> HTTP 组装 ==> TCP 握手 ==> 服务器处理 ==> 响应数据 ==> 断开连接
```

为什么不能一直连接 TCP 呢？

首先，之前提到过客户端和服务端每次建立一个 TCP 连接，都会在本地开启一块内存空间。

如果一个页面发起多个 Ajax、JS、CSS 的请求，且都使用同一个 TCP 连接，对于客户端还好，如果是服务端就会开启大量的内存空间（因为不只一台客户端向服务器发起请求），所以就必须进行销毁过期的连接，再建立新的连接来节约服务端的资源。

不过现在的 HTTP 版本已经有一些优化了。
