我们首先将浏览器渲染的整体流程进行一个概述。

浏览器作为和互联网交互的一个重要入口，在日常的生活中变得不可或缺，当我们在浏览器的地址栏输入一个网址并按下回车键后，浏览器的背后做了很多的工作。

去除 DNS 查找这些细枝末节的工作，整体的大部分可以分为两个，那就是「网络」和「渲染」。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739844986969-c5c94c44-2bd0-4718-8acc-4cb3bb3d7b7c.png)

> 网络线程和渲染主线程不属于同一个引擎：
>
> + 引擎是一个处理特定任务的组件，通常由多个线程来执行。
> + 线程是执行任务的基本单位，它在操作系统中负责执行引擎中的具体操作。
>

首先浏览器的网络线程会发起一个 HTTP 请求，和服务器之间进行通信，之后将拿到的 HTML 封装成一个渲染任务，并将其传递给渲染主线程的消息队列。

在事件循环机制的作用下，渲染主线程取出消息队列中的渲染任务，并开启渲染流程。

整体的渲染流程分为多个阶段：解析 HTML、样式计算、布局、分层、生成绘制指令、分块、光栅化、绘制；

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739845917693-a678cfd5-35b9-4552-b479-4015bbae6c2f.png)

每个阶段都有明确的输入和输出，上一个阶段的输出会成为下一个阶段的输入。这样整体的渲染流程就形成了一套组织严密的生产流水线。

## 🔢 解析 HTML
首先第一步就是解析 HTML，生成 DOM 树。

当我们打开一个网页的时候，浏览器会请求对应的 HTML 文件，虽然我们写代码的时候会分 HTML、CSS、JS，其实都是字符串，但是计算机硬件是无法理解这些字符串的，所以在网络中传输的内容其实都是 0 和 1 这些字节数据。

当浏览器接收到这些字节数据后，它会将这些字节数据转换为字符串，也就是开发者实际写的代码。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739846163327-055c892b-01c8-442f-abb9-bc421457d152.png)

当数据转换为字符串后，浏览器会先将这些字符串通过「词法分析」转化为「标记（Token）」，这个过程在词法中也叫做「标记化（Tokenization）」。

为什么需要进行标记化？原因很简单，现代浏览器虽然将字节数据转换为了字符串，但是此时的字符串如同一篇段落全部写在一行的文章一样，浏览器依然是无法理解的。

例如：

```html
<!DOCTYPE html><html lang="en"><head><title>Document</title></head><body><p>this is a test</p></body></html>
```

所以就需要进行标记化，本质上就是将这一长长的字符串拆分成一块一块的，并给这些内容打上标记，便于理解这些最小单位的代码是什么意思。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739846444491-3117081a-b4bd-44e8-916c-e6851be66aad.png)

将整个字符串进行标记后，就可以在这个基础上构建出对应的 DOM 树。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739846493761-c7f6ff7a-3d4e-4bef-b0a1-7a50a2cdbcec.png)

上面的步骤，我们称之为解析 HTML，整个流程如下：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739846526401-9d22f7b6-12e6-43f4-95af-104a33ea2368.png)

在解析 HTML 的过程中可能还会遇到`<style>`、`<link>`这些标签，此时就会涉及到 CSS 的解析。

为了提高解析的效率，浏览器在开始解析之前会启动一个预解析的线程，率先下载 HTML 中外部的 CSS 文件和外部的 JS 文件。

如果主线程解析到`<link>`的位置，此时外部的 CSS 文件还是没有下载解析好，主线程不会继续等待，继续解析后续的 HTML，这是因为下载和解析 CSS 的工作都是在预解析线程中进行的，这就是 CSS 为什么不会阻塞 HTML 解析的根本原因。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739847123109-2deb263c-cb01-447e-8dcf-d166331210cd.png)

最终 CSS 的解析在经历了从字节数据、字符串、标记化后，最后也形成了一颗 CSSOM 树。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739848331805-f575cde1-7ead-4bda-b7db-b7053ce281c5.png)

预线程处理下载解析 CSS 还会下载解析 JS，当主线程解析到`<script>`的时候，会「停止」对 HTML 的解析，转而等待 JS 文件下载好，并将全局代码执行完成后，才能继续解析 HTML。

主线程为什么要停止对 HTML 的解析呢？

这是因为 JS 代码的执行过程中，可能会影响当前的 DOM 树，所以 DOM 树的生成必须暂停，这就是 JS 会阻塞 HTML 解析的根本原因。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739848552953-6ff297ee-e4b3-458b-9697-7db3a052bd25.png)

所以，我们如果想要首屏渲染的更快，就不能在 HTML 的最前面加载 JS，这就是为什么建议将`<script>`标签放在`<body>`标签底部的原因。

```html
<html>
  <head>
    ...
  </head>
  <body>
    <p></p>
    <script src="..."></script>
  </body>
</html>
```

 另外，现代浏览器为我们提供了新的方式来避免 JS 代码阻塞渲染的情况，那就是资源提示符：

- `async`
- `defer`
- `preload`
- `prefetch`

总结一下这一阶段的成果，这个阶段完成后会得到 DOM 树和 CSSOM 树，浏览器的默认样式、内部样式、外部样式、行内样式均在 CSSOM 树中。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739848820628-85729470-323e-4d8a-a450-be5afb5b6630.png)

## 🔢 样式计算
拥有了 DOM 树浏览器还是不能知道页面的外貌，因为开发者通常会为页面的元素设置一些样式。主线程会遍历得到的 DOM 树，依次为树中的每个节点计算出它的最终样式，称为 Computed Style。

这个过程中，很多预设值都会变成绝对值，例如`red`会转换为`rgb(255, 0, 0)`，相对单位转换为绝对单位，例如`em`转化为`px`。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739849078615-b8933d4e-3481-4c2d-b443-e0c1f4a4cae3.png)

浏览器会确定每一个节点的样式到底是什么，并最终生成一颗样式规则树，这棵树上面记录了每一个 DOM 节点最终的样式。

这里的浏览器确认每一个节点的样式是指：样式计算时会对所有的 DOM 节点计算出所有的样式属性值。如果开发中没有写某一项的样式，则大概率使用的是默认值。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739849386760-b91b0bf3-46e9-445f-9ea7-dbcaed6d0c65.png)

完成这一步后，就可以得到一颗带有样式的 DOM 树。也就是说经过样式计算后，之前的 DOM 树和 CSSOM 树合并成一颗带有样式的 DOM 树。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739849472471-c03b9333-030b-4b44-ab9a-a3fe1f0e7eee.png)

## 🔢 布局
得到最新的 DOM 树之后，渲染进程就已经知道页面的具体文档结构以及每个节点拥有的样式信息了，但是这些信息还是不能最终确定页面的样子。

例如，你通过电话告诉你的朋友你刚看到的一个场景：画布上有一个红色的大圆圈和一个蓝色的正方形。单凭这些信息你的朋友还是很难知道这幅画具体是什么样子的，因为他不知道大圆圈和正方形在画布中具体的位置。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739850055519-3e8d9e6d-f415-4d99-8c43-e819b7bdad96.png)

渲染网页也是这个道理，只知道网站的文档流以及每个节点的样式还是不足以渲染出页面的内容，还需要通过布局 Layout 来计算出每个节点的几何信息 Geometry。

生成布局树的具体过程是：主线程会遍历刚刚构建出的 DOM 树，根据 DOM 节点的计算样式计算出一个布局树（Layout Tree）。布局树上的每个节点会有它在页面上 X、Y 坐标以及盒子大小的具体信息。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739850261584-58435e48-17cf-44ef-afec-54f523090d10.png)

布局树大部分的时候和 DOM 树并非一一对应的，虽然它长得和先前构建的 DOM 树差不多，但是不同的是这棵树只有那些可见的节点信息。

例如`display: none`的节点没有几何信息，因此不会生成到布局树中。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739850376183-099a1230-88cd-40f0-9138-551e6d2dc535.png)

又比如使用了伪元素选择器，虽然 DOM 树中不存在这些伪元素的节点，但是它们拥有几何信息，所以会生成到布局树中。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739850457621-b2cb3fd0-7b25-42c3-99ae-2e33cbba69ab.png)

还有匿名行盒、匿名块盒等等都会导致 DOM 树和布局树无法一一对应。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739850541959-793357cc-8f27-4ab1-bedf-a0e88f3978ac.png)

## 🔢 分层
分层的好处在于，将来某一层改变后，仅仅会对该层进行后续的处理，不会影响到其他层，从而提升效率。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739860330357-2e4e5b4d-4537-48bf-b500-448c2b6acb05.png)

为了确定哪些元素需要放置在哪一层，主线程需要遍历整颗布局树来创建一颗层次树 Layer Tree。

例如使用谷歌浏览器查看页面的图层：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739860468899-1dbe1750-92fc-41c1-bf99-fc26e1a9b9a7.png)

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739860413935-f012037b-8464-4bd3-8ec2-e7e96063043f.png)

滚动条、堆叠上下文、`transform`、`opacity`等样式都会或多或少的影响分层结果，也可以通过使用`will-change`属性告诉浏览器对其进行分层。

## 🔢 生成绘制指令
分层工作结束后，接下来就是生成绘制指令。

主线程会为每个层单独产生绘制指令集，用于描述这一层的内容该如何画出来（每一个图层都对应一个指令集）。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739860674811-823b5b1a-1257-4428-a755-320aacddbef2.png)

这里的绘制指令，类似于“将画笔移动到 xx 位置，放下画笔，绘制一条 xx 像素长度的线”，我们在浏览器中看到的各种复杂的页面，实际上都是这样一条条的指令所绘制的。

如果你熟悉 Canvas，那么指令就类似于：

```js
context.beginPath(); // 开始路径
context.moveTo(10, 10); // 移动画笔
context.lineTo(100, 100); // 绘画出一条直线
context.closePath(); // 闭合路径
context.stroke(); // 进行勾勒
```

不过要注意，这一步只是生成绘制的指令，还没有开始执行这些指令。

另外还有一个重要的点需要知道，生成绘制指令集后，渲染主线程的工程就告一段落了，接下来主线程将每个图层的绘制信息都提交给「合成线程」，剩余的工作将由合成线程完成。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739860965084-521b2af5-b341-4e7b-9d65-ef8315fe5b43.png)

## 🔢 分块
合成线程首先对每个图层进行分块，将其划分为更多的小区域。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739861034367-4f4941ad-4308-4c37-a2f8-5313ae5a3ea5.png)

此时，它不再是像主线程那样一个人在战斗，它会从线程池中拿取多个线程来完成分块工作。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739861092708-fd267b60-9841-4f6c-b104-2b49da6da875.png)

## 🔢 光栅化
分块完成后进入光栅化阶段。所谓光栅化，就是将每个块变成位图（可以理解为每一个像素点）。

更简单的理解就是确认每一个像素点的 RGB 信息，如下图所示：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739861187099-76e232cd-17d3-40bf-a45e-602d8968395f.png)

光栅化的操作并不是由合成线程来做的，而是由合成线程将块信息交给 GPU 进行，以极高的速度完成光栅化。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739861308096-b3a6b6ac-23b3-4ec9-818c-353ae24a9fa1.png)

GPU 进程会开启多个线程来完成光栅化，并且优先处理靠近视口区域的块。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739861356099-4bb0c8c4-02d2-485e-be46-bdad938c4608.png)

## 🔢 绘制
最终才来到绘制的步骤，当所有的图块都被光栅化之后，合成线程会拿到每个层、每个块的位图，从而生成一个个的指引 Quad 信息。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739861538505-bc8ac0c3-7344-4dc2-964b-a7b7ff934256.png)

指引会标识出每个位图应该画到屏幕的哪个位置上，以及考虑到旋转、缩放等变形。

变形发生在在合成线程，与渲染主线程无关，这就是`transform`效率高的本质原因。

合成线程会通过 IPC 向浏览器进程（browser process）提交一个渲染帧。这个时候可能有另外一个合成帧被浏览器进程的 UI 线程提交以改变浏览器的 UI，这些合成帧都会被发送给 GPU 完成最终的屏幕成像。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739861726786-615e2646-4100-4f76-a514-134d8ca4c54f.png)

## 🔢 回流与重绘
什么是 Reflow（回流）？

Reflow 的本质就是重新计算 Layout 树，当进行了影响布局树的操作后（如改变元素的尺寸、位置、字体等），需要重新计算布局树。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739862576697-7ccccc3b-b1f5-4464-9645-b2ee8d064eb6.png)

所以为了避免连续的多次操作导致布局树反复计算，浏览器会合并这些操作。当 JS 代码全部执行完成后再统一进行计算，所以改动属性造成的 Reflow 是异步完成的。

也同样因为这个原因，当 JS 获取布局属性的时候，就可能造成无法获取到最新的布局信息。

浏览器在反复权衡下，最终决定在「获取属性的时候立即开始 Reflow」。

```js
const op = document.querySelector(".test");
op.style.marginLeft = "100px";
op.style.marginLeft = "150px";
op.style.marginLeft; // 立即触发 Reflow
op.style.marginLeft = "200px";
```

JS 什么情况下会引起 Reflow？

1. 修改元素的尺寸和位置；
2. 添加或修改 DOM 的结构；
3. 更改元素的显示方式，例如`display: block/none`（`visibility: hidden`会引起重绘）；
4. 更改元素的盒模型`box-sizing`;
5. 更改滚动条；
6. 更改窗口的大小；
7. 获取元素的布局属性；

什么是 Repaint（重绘）呢？

Repaint 的本质就是重新根据分层信息计算了绘制指令。

当改动了可见样式后，就需要重新计算，会触发 Repaint。

由于元素的布局信息也属于可见样式，所以 Reflow 一定会引起 Repaint，反过来则不会。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739862835389-c86bc909-1155-468d-abc5-98aa80211788.png)

如何减少页面的 Reflow 和 Repaint？

1. 利用`display: none;`属性。

```js
var oBox = document.getElementById("box");
var boxStyle = oBox.style;

boxStyle.display = "none"; // 回流+重绘
boxStyle.width = "100px";
boxStyle.height = "100px";
boxStyle.margin = "10px";
boxStyle.padding = "10px";
boxStyle.backgroundColor = "black";
boxStyle.border = "1px solid red";
boxStyle.color = "#fff";
boxStyle.fontSize = "32px";
boxStyle.display = "block"; // 回流+重绘
```

2. 给元素设置类名。

```js
// 在 css 中定义好 .active
// .active{...}

var oBox = document.getElementById("box");
oBox.className += " active"; // 这样只会引起一次回流+重绘
```

3. 创建文档碎片。

```js
var frag = document.createDocumentFragment();
for (let i = 0; i < 10; i++) {
  frag.appendChild(document.createElement("li"));
}

document.body.appendChild(frag);
```

4. 缓存元素的布局属性。

```js
var oBox = document.getElementById("box");
var offset = oBox.offsetWidth;

div.style.width = offset + 10 + "px";
```

为什么`transform`的效率更高呢？

因为`transform`既不会影响布局，也不会影响绘制指令，它的影响只是渲染流程的最后一个 Draw 阶段。

由于 Draw 阶段在合成线程中，所以`transform`的变化几乎不会影响渲染主线程。反过来，渲染主线程无论多忙碌，也不会影响`transform`的变化。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/5%20%E6%B5%8F%E8%A7%88%E5%99%A8%E4%B8%8E%E7%BD%91%E7%BB%9C/%E6%B5%8F%E8%A7%88%E5%99%A8/_assets/1739863082553-5b28bd00-ecd2-42a8-9ad6-caa3ddefcfdc.png)
