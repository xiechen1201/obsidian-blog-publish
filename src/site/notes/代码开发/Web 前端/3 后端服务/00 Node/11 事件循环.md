在讲述 Node 事件循环之前，我们很有必要先对浏览器的事件循环有个初步的了解。

[事件循环](https://www.yuque.com/xiechen/gs6rno/hns6d5lyl4u9cc7d)

Node 中的事件循环和浏览器的事件循环是完全不相同的东西。

Node 采用 V8 作为 JS 的解析引擎，而 I/O 处理方面使用了自己设计的 libuv，libuv 是一个基于事件驱动的跨平台的抽象层，使用 C++ 编写，封装了不同操作系统一些底层特性，对外提供统一的 API，事件循环机制也是它里面的实现。

浏览器事件循环示意图：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/3%20%E5%90%8E%E7%AB%AF%E6%9C%8D%E5%8A%A1/00%20Node/_assets/1749449879413-37fb175c-6ff5-456a-9d6d-3130e5f5f705.png)

> 根据最新的 W3C 规范和浏览器实现，浏览器事件循环机制已不再简单划分为微任务（Microtask）和宏任务（Macrotask），而是采用了更复杂的多队列优先级模型，这里的图依然是旧规范中的两种事件队列。
>
> 任务队列按类型和优先级划分：
>
> 1. 微任务队列（Microtask Queue）
>     - 仍然存在且优先级最高，包含`Promise`、`MutationObserver`等；
>     - 必须在当前宏任务执行完后立即清空，且优先于其他队列；
> 2. 交互队列（User Interaction Queue）
>     - 处理用户触发的任务（如点击、滚动事件），优先级高于普通宏任务；
> 3. 延时队列（Timer Queue）
>     - 包含`setTimeout`、`setInterval`等，优先级较低；
> 4. 其他专用队列
>     - 如网络请求、`MessageChannel`等，浏览器可能动态调整优先级；
>
> 详见：[https://html.spec.whatwg.org/multipage/webappapis.html#event-loops](https://html.spec.whatwg.org/multipage/webappapis.html#event-loops)
>

可以看到，Node 的事件循环要比浏览器复杂的多，Node 的运行机制如下：

- V8 引擎解析 JavaScript 脚本；
- 解析后的代码，调用 Node API；
- libuv 库负责 Node API 的执行，它将不同的任务分配给不同的线程，形成一个事件循环，以异步的方式将任务的执行结果返回到 V8 引擎；

## 事件循环的 6 个阶段
其中 Libuv 引擎中的事件循环分为 6 个阶段，它们会按照顺序反复运行。每当进入某一个阶段的时候，都会从对应的回调队列中取出函数去执行。当当前队列为空或者执行的回调函数数量达到系统设定的阈值，那么就会进入下一个阶段。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/3%20%E5%90%8E%E7%AB%AF%E6%9C%8D%E5%8A%A1/00%20Node/_assets/1749453947446-e8523172-e32a-4f65-a7ab-b3cd33f8656c.jpeg)

从图中可以看到，Node 大致的事件循环顺序：

外部输入数据 --> 轮询阶段（poll）--> 检查阶段（check）-->关闭事件回调阶段（close callback）--> 定时器检测阶段（timer）--> I/O 事件回调阶段（I/O callbacks）--> 闲置阶段（idle, prepare）--> 轮询阶段（poll）（按照这个顺序反复运行）...

以上 6 个阶段所做的事情如下：

- timers 阶段：这个阶段执行 timer（`setTimeout()`、`setInterval()`）的回调；
- I/O callbacks 阶段：处理一些上一轮循环中的少数未执行的 I/O 回调；
- idle、prepare 阶段：仅 Node 内部使用；
- poll 阶段：获取新的 I/O 事件、网络、读取文件等，适当的条件下 Node 将阻塞在这里；
- check 阶段：执行`setImmediate()`的回调；
- close callbacks 阶段：执行 socket 的 close 事件回调；

<br/>warning
⚠️ 注意

上面六个阶段都不包括`process.nextTick()`。

<br/>

接下来，详细介绍 timers、poll、check 这 3 个阶段，因为日常开发中绝大部分异步任务都是在这 3 个阶段去处理的。

## timer 阶段
`timer`阶段会执行`setTimeout`和`setInterval`回调，并且是由 poll 阶段控制的。同样，在 Node 中定时器指定的时间也不是准确的时间，只能是尽快执行。

## poll 阶段
poll 阶段是一个至关重要的阶段，在这个阶段中，系统会做两个事情：

- 回到 timer 阶段执行回调；
- 执行 I/O 回调；

并且在进入该阶段的时候，如果没有设定 timer 的话，会发生以下两件事情：

- 如果 poll 队列不为空，会遍历回调队列并且同步执行，直到队列为空或者达到系统限制；
    - ![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/3%20%E5%90%8E%E7%AB%AF%E6%9C%8D%E5%8A%A1/00%20Node/_assets/1749462407863-f32529c1-ddbc-4e87-8069-c3f7b26c7eea.png)
- 如果 poll 队列为空时，会有两件事情发生：
    - 如果`setImmediate`（其属于 check 阶段）回调需要执行，poll 阶段会停止并且进入到 check 阶段执行回调；
    - 如果没有`setImmediate`回调需要执行，会在 poll 阶段一直等待，当回调被加入到队列中会立即执行回调，这里同样会有个超时时间设置，防止一直等待下去；
    - ![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/3%20%E5%90%8E%E7%AB%AF%E6%9C%8D%E5%8A%A1/00%20Node/_assets/1749462544781-b7f7f40e-73aa-444f-b98d-37b710d00385.png)

当然设定了 timer 的话，且 poll 队列为空时，则会判断是否有 timer 超时，如果有的话会回到 timer 阶段执行回调。

假如 poll 被堵塞，那么即使 timer 已经到时间了也只能等着，这也是为什么上面说定时器指定的时间并不是准确的时间。

示例：

```js
const start = Date.now();
// 两秒后将回调函数推入 timer 队列
setTimeout(function f1() {
  console.log("setTimeout", Date.now() - start);
}, 200);

const fs = require('fs');

// 读取文件
fs.readFile('./index.js', 'utf-8', function f2() {
  console.log('readFile');
  const start = Date.now();
  // 强行延时 500 毫秒
  while (Date.now() - start < 500) { }
})
```

```latex
readFile
setTimeout 507
```

可以看到，`setTimeout`的回调在 507 毫秒后才被执行。

执行过程中，队列内容如下：

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/3%20%E5%90%8E%E7%AB%AF%E6%9C%8D%E5%8A%A1/00%20Node/_assets/1749463117615-63f3a5ba-0012-4e96-becd-99564346e34c.png)

因为 poll 队列先执行，所以先打印出“readFile”（强制延时的过程中，`setTimeout`的回调会被推入到 timer 队列中），最后才会往下执行到 timer 队列打印出“setTimeout 507”。

为了证明 poll 队列是连续执行的，我们可以再添加一个 I/O 任务：

```js
const start = Date.now();
setTimeout(function f1() {

}, 200);

const fs = require("fs");

fs.readFile("./index.js", "utf-8", function f2() {
    console.log("readFile1");
    const start = Date.now();
    while (Date.now() - start < 500) {}
});

fs.readFile("./index.js", "utf-8", function f2() {
    console.log("readFile2");
    const start = Date.now();
    while (Date.now() - start < 500) {}
});
```

只有当 poll 队列所有回调执行完成后，才会往下执行，timer 队列的任务只能一直等着被执行。

## check 阶段
`setImmediate()`的回调会被添加到 check 队列中，从事件循环的阶段图中可以看出，check 阶段的执行顺序在 poll 阶段之后。

示例：

```js
console.log('start')

setTimeout(() => {
  console.log('timer1')
  Promise.resolve().then(function() {
    console.log('promise1')
  })
}, 0)

setTimeout(() => {
  console.log('timer2')
  Promise.resolve().then(function() {
    console.log('promise2')
  })
}, 0)

Promise.resolve().then(function() {
  console.log('promise3')
})

console.log('end')

// 输出结果：start => end => promise3 => timer1 => promise1 => timer2 => promise2
```

以上代码中，一开始执行同步任务，依次打印出“start”、“end”，并将 2 个 timer 依次放入 timer 队列中，之后会立即执行微任务队列，所以打印出“promise3”。

然后进入 timers 阶段，执行 timer1 的回调函数，打印 timer1，发现有一个`promise.then`的回调将其加入到微任务队列并且立即执行，之后同样的步骤执行 timer2，打印“timer2”以及“promise2”。

⚠️ 一些注意点：

`setTimeout`和`setImmediate`的区别，两者非常的相似，区别主要在于调度时机不同。

- `setImmediate`设计在 poll 阶段完成时执行，即 check 阶段；
- `setTimeout`设计在 poll 阶段空闲的时候，且设定时间到达后执行，但它在 timer 阶段执行；

示例：

```js
setTimeout(function timeout() {
    console.log("timeout");
}, 0);

setImmediate(function immediate() {
    console.log("immediate");
});
```

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/3%20%E5%90%8E%E7%AB%AF%E6%9C%8D%E5%8A%A1/00%20Node/_assets/1749522828848-757b78b7-3adc-4e8f-a37f-09279d6b84e2.png)

对于上面的代码，`setTimeout`可能先执行，也可能是`setImmediate`先执行。首先`setTimeout(fn, 0) === setTimeout(fn, 1)`这是由源码决定的，进入事件循环也是需要成本的，如果在准备的时候花费了 1ms 的时间，那么在 timer 阶段就会直接执行`setTimeout`的回调。如果准备时间小于 1ms，那么就是`setImmediate`回调先执行了。

但是当二者在异步 I/O callback 内部调用的时候，总是先执行`setImmediate`，再执行`setTimeout`，例如：

```js
const fs = require("fs");

fs.readFile(__filename, () => {
  setTimeout(() => {
    console.log("timeout");
  }, 0);

  setImmediate(() => {
    console.log("immediate");
  });
});

/*
    immediate
    timeout
*/
```

在上面的代码中，`setImmediate`永远最先执行，这是因为两个函数都写在 I/O 回调中，I/O 回调 是在 poll 阶段执行，当回调执行完毕后队列为空，发现存在`setImmediate`回调，所以就直接跳转到 check 阶段去执行回调了。

## process.nextTick
这个函数其实是独立于事件循环之外的，他有一个自己的队列。当每个（也就是上面说的 6 个阶段）阶段完成后，如果存在 nextTick 队列，就会清空微任务队列中的所有回调函数，并且优先于其他 microtask 执行。

`process.nextTick`其实也是进入微任务队列，但是优先级又比`Promise.then`更高。

```js
setTimeout(() => {
  console.log("timer1");
  Promise.resolve().then(function () {
    console.log("promise1");
  });
}, 0);

process.nextTick(() => {
  console.log("nextTick");
  process.nextTick(() => {
    console.log("nextTick");
    process.nextTick(() => {
      console.log("nextTick");
      process.nextTick(() => {
        console.log("nextTick");
      });
    });
  });
});

/*
    timer 队列：setTimeout
    微任务队列：nextTick、nextTick、nextTick、nextTick

*/

// nextTick => nextTick => nextTick => nextTick => timer1 => promise1
```

## Promise.then
`Promise.then`也是独立于事件循环之外的，有一个自己的队列，但是优先级要比`process.nextTick`要低，所以当微任务中同时出现`process.nextTick`和`Promise.then`的时候，会优先执行前者。

示例：

```js
setTimeout(() => {
    console.log("timer1");
    Promise.resolve().then(function () {
        console.log("promise1");
    });
    process.nextTick(() => {
        console.log("nexttick");
    });
}, 0);

setTimeout(() => {
    console.log("timer2");
    Promise.resolve().then(function () {
        console.log("promise2");
    });
}, 0);

/*
    执行第一个 setTimeout 时队列情况：
    timer 队列：setTimeout、setTimeout
    微任务队列：promise、process
*/

// timer1、nexttick、promise1、timer2、promise2
```

## Node 和浏览器事件循环的区别
在浏览器环境下，就两个队列，一个是宏任务队列，另外一个是微任务队列。微任务队列中的任务是在每个宏任务执行完毕之后执行的。

在 Node 中，每个任务队列的每个任务执行完毕之后，就会清空这个微任务队列。

![](/img/user/%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/3%20%E5%90%8E%E7%AB%AF%E6%9C%8D%E5%8A%A1/00%20Node/_assets/1749529653195-07498675-cd5d-4a1a-8ac3-1f7ece095397.png)

其主要的区别就在于执行的时机不同。
