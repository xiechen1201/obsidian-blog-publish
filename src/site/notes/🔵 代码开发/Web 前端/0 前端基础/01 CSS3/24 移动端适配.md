## 🔢 什么是 WebAPP？
在早期的手机时代，根本不存在手机应用的概念，基本上就是你买一个手机，手机上有什么功能，你就用什么功能。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749633899955-3955acf5-b8b6-4991-a438-7ee01cd7a6fc.png)

后来随着时代和技术的发展，智能手机开始涌现，iOS 和 Andriod 两大手机系统阵营占领了半壁江山，手机也开始演变成为以应用（Application）为主的形态。

刚开始的时候智能手机的应用也不多，智能手机都提供了一个称为“应用市场”的平台，允许开发者上架自己的 APP 到“市场”中去。

但是，因为 iOS 和 Andriod 用户体量都不小，所以开发一款 APP 就需要使用不同的开发语言去开发 APP，也就是需要至少两个程序员分别开发不同系统的 APP。针对不同系统开发出的 APP 被称为「原生应用（Native APP）」，无论从性能还是体验上来讲都是最好的。

那么到底是什么原因让前端开发者也参与到开发 APP 的浪潮呢？

那就是手机浏览器！

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749634336682-2fe89266-9586-45ca-a137-ee45fc71d9e9.png)

在智能手机刚开始普及的时候，智能手机就已经拥有浏览器的应用了，只不过最初在手机上使用浏览器访问网页的体验并不好，例如每点击一个连接都会导致页面整体刷新，而且那个年代的网速还非常的慢。

另外，那个年代手机浏览器也只能预览 PC 端的网页，看网页内容的时候非常小，体验很糟糕。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749634523820-9597ec14-e6ce-46f6-bd8a-d27ad054bf66.png)

伴随着 HTML5、CSS3 的推出，SPA（Single Page Application）开发模式的流行，4G 通信技术的出现，网站给用户带来的体验也越来越好，让人越来越觉得是在使用一个应用，而不是一个网站。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749634636052-5402bddd-36f9-4626-a845-7b36c708f2aa.png)

因此，现在说 WebAPP 更多的是指移动端的网站或者 H5 应用，说白了就是特定允许在移动端浏览器上的网站应用。

WebAPP 相对比元素应用又具有以下优缺点：

优点：

- 开发成本低，可以跨平台使用，调试方便开发速度快；
- 维护成本低；
- 更新速度快；
- 无需安装手机 APP 就可以直接访问使用；

缺点：

- 性能不好，用户体验差；
- 强依赖于网络，页面访问速度慢；
- 功能受限，特殊功能无法实现；
- 临时性入口，用户留存率低；

## 🔢 什么是 WebView？
说完 WebAPP 我们再来说说什么是 WebView。

简单说，WebView 就是显示 WebAPP 的区域。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749634947224-7224866d-e4da-4e98-93e6-142bdcef3bc9.png)

上图中，当使用百度、抖音、默认浏览器、微信、支付宝都可以打开猫眼的页面，这因为这些原生 APP 都具有 WebView 的能力。

WebView 就是一个嵌入式的浏览器，原生 APP 可以使用它来展示网页的内容。简单理解就好像是原生的 APP 使用`<iframe>`标签嵌入了一个网页。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749635176735-aaafb7da-d75a-4859-a0be-48b9c8ad944c.png)

运行在 WebView 中的网页是可以和原生 APP 进行交互的，这也就意味着网页不必在遵守传统浏览器安全沙箱的限制。

例如：

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749635287832-f04f306e-0ef9-4cb0-b798-b174d39492a8.png)

Web 端的代码和原生应用的代码相互交互，这种模式通常被称为 bridge。因为 bridge 的存在，Web 网页只要运行在 WebView 中就可以调用原生应用提供的 API，完成一些更高级深入的功能了。

## 🔢 移动端像素
进入智能手机时代后，在开发移动端 Web 页面的时候，由于手机屏幕的尺寸、分辨率不同，又或者是需要考虑横竖屏的问题，为了让一套 Web 页面在不同设备上具有相同的展示效果，就需要在开发过程中使用合理的适配方案来解决适配的问题。

首先，我们需要明白几个概念：

- 设备像素（物理像素）；
- 屏幕尺寸和像素密度（PPI）；
- CSS 像素（设备独立像素、逻辑像素）；
- 像素比；

## 🔢 设备像素（物理像素）
设备像素也称为物理像素，也是一个非常好理解的名称，对于一般的设备来说，一个像素对应着屏幕上的一个发光点，这个点能发出红、绿、蓝三种颜色的光，通过混合不同的 RGB 值，为我们创造了一个像素的颜色。

因此，设备像素就是指实际存在的像素。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749635818061-9c7785cc-07d4-4424-bfd6-5c406a9a1611.png)

当我们在看一个设备屏幕参数的时候，往往也会有分辨率这个参数。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749635899644-1c646a9c-ce25-4f44-9fd7-4c722231c3be.png)

这就是表示设备的屏幕上横向有 2560 个像素点，纵向有 1600 个像素点，横向和纵向的像素点越多，我们肉眼的观看效果越好。

## 🔢 屏幕尺寸和像素密度（PPI）
明白了设备像素后，接下来再看两个概念，屏幕尺寸和像素密度（PPI）。

我们在买手机的时候经常会听到一个手机信息 xx 英寸，那么英寸到底是什么呢？难道是屏幕的面积吗？

实际上，英寸是一个长度单位，1 英寸等于 2.54 厘米，其次英寸指得是屏幕对角线的长度。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749637608237-42c3c2c2-167e-4c6c-b5b4-138d9694fcf5.png)

有了屏幕分辨率和屏幕尺寸的信息后，我们就可以计算像素密度（PPI）了。所谓像素密度就是指 1 英寸下有多少设备像素，计算公式：

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749637678672-4d5c0975-d296-4418-9c77-9e266c1b5487.png)

这里我们可以简单计算一下 iPhone6 Plus 的 PPI：

```js
// 屏幕斜边的像素
const margin = Math.sqrt(Math.pow(1080,2) + Math.pow(1920,2));
console.log(margin); // 2202.9071700822983
console.log(margin/5.5); // 400.52857637859967 PPI
```

可以看到计算的结果和 Apple 宣传时的 PPI 基本一致，也就是 iPhone6 Plus 的 PPI 值为 401。

这里有一个网站，可以查看一些常见设备的 PPI 值：

[DPI Calculator / PPI Calculator](https://www.sven.de/dpi/)

## 🔢 CSS 像素（设备独立像素、逻辑像素）
什么又是 CSS 像素呢？

上面我们刚讲完 PPI 的概念，那么 PPI 的值越高，包包含的设备像素也就越多，自然而然的屏幕的显示效果也就更好（因为更加的精细）。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749637924378-582a5916-c9dc-48b4-b184-20d83a88ebbc.png)

但是此时又出现另外一个问题，如果我的 CSS 像素和设备像素是 1:1 的关系，随着设备像素的提升，图像就会变得越来越小了。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749638007577-5b89e97f-cc04-4ebc-bdcb-7a7629d1fd7b.png)

那么如何解决这个问题呢？

其实也非常好办，之前 CSS 像素和设备像素是 1:1 的关系，我们现在只需要将这个比例稍微修改一下即可。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749638082291-86b44ea4-0c20-464e-ba11-6f953777a977.png)

如图所示，之前在 1:1 关系的时候，1 个 CSS 像素就对应 1 个设备像素，那么我修改比例后 1 个 CSS 像素对应 2 个设备像素即可（宽 * 高就是 4 个设备像素）。

之前在做 PC 端网页的时候，由于 CSS 像素始终和设备像素是 1:1 的关系（不考虑缩放的情况），所以给很多人一种错觉，认为 CSS 像素和设备像素就是 1:1 的对应关系，但实际上 CSS 像素是一个「抽象单位」，具体 1 个 CSS 像素对应几个设备像素是不确定的。

## 🔢 像素比（DPR）
像素比 DPR 的全称是 device pixel ratio（设备像素比），计算公式为：DPR = 设备像素 / CSS 像素。

举个例子，如果 CSS 像素和设备像素是 1:1 的关系，那么 DPR 的值就为 1，如果 1 个 CSS 像素对应 2 个设备像素，那么 DPR 的值就为 2。

说的简单一点，就是 1 个 CSS 像素要用多少个设备像素来显示。如果 DPR 为 1，就表示 1 个设备像素就够了，如果 DPR 为 2，则表示一个 1 个 CSS 像素要用 2 个设备像素来显示。

我们以 iPhone6 为例，iPhone 官方给出的分辨率为 1334 x 750，假如我们设置一个`<div>`，宽度为 375 却能撑满整个手机：

```html
<div></div>
```

```css
*{
  margin:0;
  padding:0;
}

div{
  width: 375px;
  height: 100px;
  background-color: red;
}
```

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749798038389-5b685f16-fe1c-44cf-b661-35bc5ce91402.png)

由此我们可以推测，一个 CSS 像素和设备像素的对应关系为 1:2，那么 DPR 就应该是 2，通过查看`window.devicePixelRatio`的值发现也确实为 2。

```js
console.log(window.devicePixelRatio); // 2
```

## 🔢 viewport 视口
viewport 视口是指设备的屏幕上用来显示我们网页的那一片区域，在具体一点就是浏览器上（也可能是 APP 的 WebView）用来显示网页的那部分区域。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749794100082-dfd25ea6-04ef-4c2a-bf3e-9bfae7aa352d.png)

在早期的 PC 年代，电脑上网页常见的宽度有：960px、980px、1190px、1210px，其中大多数都是 980px。

到了移动端时代，由于一开始并不存在专门的移动端网页，所以在最开始的时候也就自然而然的应用了 PC 端的设定，以 Apple 的 Safari 为首的浏览器默认采用的视口宽度就是 980px，后面的很多安卓机型也就沿用了这一设定。

<br/>tips
故事是这样的，有一天乔帮主在想一个问题，就是自己的苹果手机如果在市场上火爆了，但是各个网站还没有来得及制作手机版本的网页，那么用户不得不用手机访问电脑版的网页。如何用小屏幕访问大屏幕的页面也同样可读呢？

乔帮主就想着为手机固定一个视口宽度，让手机的视口宽度等于世界上绝大多数 PC 网页的版心宽度，也就是 980px。这样，用手机访问电脑版网页的时候，刚好没有留白。像从 3000 米高空，俯瞰整个页面，用户想看哪个区域，可以用两个指头捏合，放大页面。

安卓手机也非常尊重乔帮主的决定，都把自己的手机的视口定位 980px。

下面列出了一些设备上浏览器默认的 viewport 的宽度：

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749794671454-5b26d314-9e0b-4091-a1ac-2e8bc12e3751.png)

我们可以进行一个简单的验证：

```html
<head>
  <meta charset="UTF-8">
  <title>Document</title>
  <!-- <meta name="viewport" content="width=device-width, initial-scale=1.0" /> -->
  <style>
    * {
      margin: 0;
      padding: 0;
    }
    .container{
      width: 375px;
      display: flex;
    }
    .container>div{
      width: 50%;
      height: 50px;
    }
    .container>div:nth-child(1) {
      background-color: red;
    }
    .container>div:nth-child(2) {
      background-color: yellow;
    }
  </style>
</head>

<body>
  <div class="container">
    <div></div>
    <div></div>
  </div>
</body>
```

上面代码中，我们将默认的视口设置取消了，此时就会采用默认的 980px 宽度，而我们的`.container`元素设置的是 375px，效果如下：

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749794946167-d84ab7a0-e5db-4b0b-aeb8-142fe10ff242.png)

可以看到，由于默认视口的宽度为 980px，因此`.container`并没有占满，而是占了一半还不到。

后来随着移动端的发展，渐渐的专门针对移动端的网页就出来了，如下图：

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749795043340-a7f18bc9-47d1-455a-be07-ea9142d0be73.png)

此时就不能像之前一样视口一直按照 PC 端的 980px 来作为标准，因为 980px 实际上是超出设备屏幕的，只不过浏览器智能的进行了缩放。

这个时候就应该按照设备的 CSS 像素作为标准，还记得 iPhone6/7/8 的 CSS 像素是多少吗？没错，是 375 x 667，也就说现在的网页就应该按照 375 的标准。

## 🔢 视口的分类
[ppk](https://www.quirksmode.org/) 大神对于移动端上的 viewport 有非常多的研究（[第一篇](https://www.quirksmode.org/mobile/viewports.html)、[第二篇](https://www.quirksmode.org/mobile/viewports2.html)、[第三篇](https://www.quirksmode.org/mobile/metaviewport/)），ppk 认为移动设备有 3 个 viewport，分别是：

- layout viewport
- visual viewport
- ideal viewport

ppk 把浏览器默认的 viewport（也就是 980px 宽度的 viewport）叫做 layout viewport，这个 layout viewport 的宽度可以通过`window.innerWidth`获取。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749795425150-d5ff1bd5-18ee-497a-b025-5c770168fe8c.png)

然后，layout viewport 的宽度是大于浏览器可视宽度的，所以我们还需要一个 viewport 来代表浏览器可视区域的大小，ppk 把这个 viewport 叫做 visual viewport。visual viewport 的宽度可以通过`document.documentElement.clientWidth`来获取。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749795556571-0a9d0b16-facf-419d-8fe5-310ee0379aef.png)

到现在我们已经有两个 viewport 了，layout viewport 和 visual viewport。layout viewport 是网页实际的宽度，而 visual viewport 是设备的宽度。

在早期 iPhone3GS 时代，由于 1 个 CSS 像素对应 1 个设备像素，因此 visual viewport 和设备 CSS 宽度是等价的。但是从 iPhone4 时代开始，1 个 CSS 像素对应 2 个设备像素，设备的 CSS 宽度仍然是 320px，但是物理像素翻了倍。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749795740151-79e682ec-2e93-44b6-a349-198ac582b02f.png)

于是 ppk 又发明一个新的词汇：ideal viewport，也就是第三个 viewport -- 移动端的完美适配 viewport，其实对应的就是设备的 CSS 宽度。

例如 iPhone 3GS 和 iPhone4 的 ideal viewport 宽度都是 320px，无论它的设备像素是 320px 还是 640px，这两款 iPhone 中 CSS 中的 320px 就代表 iPhone 屏幕的宽度。

最后再总结一下：ppl 把移动设备上的 viewport 分为 layout viewport、visual viewport 和 ideal viewport 三类，其中的 ideal viewport 是最适合移动设备的 viewport。

ideal viewport 的意义在于，无论在什么分辨率的屏幕下，那些针对 ideal viewport 而设计的网站，不需要用户手动缩放，也不需要出现横向滚动条，都可以完美的呈现给用户。

## 🔢 视口相关属性
移动设备默认的 viewport 是 layout viewport，也就是比屏幕要宽的 viewport，但是在进行移动端开发的时候，我们需要的是 ideal viewport，那么怎么才能得到 ideal viewport 呢？

这就轮到`<meta />`标签出场了。

我们在开发移动端网站的时候，最常见的一个动作就是把下面的这个东西复制到网页的`<head>`中去：

```html
<meta name="viewport" content="width=device-width,initial-scale=1,minimum-scale=1,maximum-scale=1,user-scalable=no">
```

这个`<meta />`标签的作用就是让当前的 viewport 设置为 ideal viewport，同时不允许用户进行缩放。

至于是否允许用户进行缩放，每个网站可能需求不一样，但是让 viewport 的宽度为 ideal viewport 这个是大家都想要的结果，如果你不这样设定的话，那么就会使用比屏幕宽的默认的 viewport，在不缩放的情况下就会出现横向滚动条。

`<mete />`的 viewport 有 6 个属性（姑且把`content`中的那些东西称为一个个属性和值），如下：

| 属性名 | 作用 |
| --- | --- |
| width | 设置 layout viewport  的宽度，为一个正整数，或字符串"device-width" |
| height | 设置 layout viewport 的高度，这个属性对我们并不重要，很少使用 |
| initial-scale | 设置页面的初始缩放值，为一个数字，可以带小数 |
| minimum-scale | 允许用户的最小缩放值，为一个数字，可以带小数 |
| maximum-scale | 允许用户的最大缩放值，为一个数字，可以带小数 |
| user-scalable | 是否允许用户进行缩放，值为"no"或"yes", no 代表不允许，yes 代表允许 |

这些属性是可以同时使用的，也可以单独使用或在混合使用，多个属性同时使用时使用逗号隔开即可。

最简单的方式就是设置`width=device-width`，表示把默认的 layout viewport 的宽度设置为移动设备的屏幕宽度。

示例：

```html
<head>
    <meta charset="UTF-8" />
    <title>Document</title>
    <meta name="viewport" content="width=device-width" />
    <style>
        * {
            margin: 0;
            padding: 0;
        }
        .container {
            width: 375px;
            display: flex;
        }
        .container > div {
            width: 50%;
            height: 50px;
        }
        .container > div:nth-child(1) {
            background-color: red;
        }
        .container > div:nth-child(2) {
            background-color: yellow;
        }
    </style>
</head>

<body>
    <div class="container">
        <div></div>
        <div></div>
    </div>
    <script>
        console.log(
            "document.documentElement.clientWidth:",
            document.documentElement.clientWidth
        );
        console.log("window.innerWidth:", window.innerWidth);
    </script>
</body>

```

```latex
document.documentElement.clientWidth: 375
window.innerWidth: 375
```

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749797439736-607754a7-7a25-4439-af90-80073d912792.png)

另外，如果我们只设置`inital-scale`为 1，也能达到同样的效果，也就是说能把当前的 viewport 变为 ideal viewport：

```html
<meta name="viewport" content="initial-scale=1">
```

这句代码的作用只是不对当前的页面进行缩放，也就是页面本该是多大就是多大，那为什么会有`width=device-width`的效果呢？

要想清楚这件事情，首先你得明白这个缩放是相对于什么来缩放的，因为这里的缩放值是 1，也即是没有缩放，但是却达到了 ideal viewport 的效果。所以，答案只有一个，那就是缩放是相对于 ideal viewport 进行缩放的，当对 ideal viewport 进行 100% 的缩放，也就是缩放值为 1 的时候，得到的不就是 ideal viewport 了吗？

但如果`width`和`initial-scale=1`同时出现，并且还出现了冲突呢？比如：

```html
<meta name="viewport" content="width=400, initial-scale=1">
```

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749797742489-21eca011-c56a-4557-b916-af016aed2b60.png)

遇到这种情况的时候，浏览器会取它们两个中最大的那个值，示例中也就是 400px。

最后，总结一下，要把当前的 viewport 宽度设为 ideal viewport 的宽度，既可以设置`width=device-width`，也可以设置`initial-scale=1`，但这两者各有一个小缺陷，就是 iphone、ipad 以及 IE 会横竖屏不分，通通以竖屏的 ideal viewport 宽度为准。

所以，最完美的写法应该是，两者都写上去，这样就`initial-scale=1`解决了 iphone、ipad 的毛病，`width=device-width`则解决了 IE 的毛病：

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

- 宽高
- 间距
- 图像

常见的适配方案有很多，这里列举出 5 种适配方案，分别是：

- 百分比

- rem
- vw 和 vh

## 🔢 百分比
在 CSS 中盒子的宽度可以设置为一个百分比值，表示根据父级宽度的百分比来计算宽度，因此我们可以通过百分比的方式让一个盒子在任何设备中的宽度都一致。

```html
<div></div>
<div></div>
<div></div>
<div></div>
```

```css
* {
  margin: 0;
  padding: 0;
}

div {
  width: 25%;
  height: 100px;
  float: left;
}

div:nth-child(1) {
  background: red;
}

div:nth-child(2) {
  background: green;
}

div:nth-child(3) {
  background: blue;
}

div:nth-child(4) {
  background: pink;
}
```

在上面的代码中，我们设置了 4 个盒子，每个盒子的宽度占比为 25%。由于设置的是百分比，因此这在任何设备中显示的比例都是一样的。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749799199089-4ed0b4a8-8792-46bd-b0ef-1781c988abb0.png)

但是这种方案通常需要配合其他的方案进行一起使用。

## 🔢 DPR 缩放
DPR 是指像素比（物理像素 / CSS 像素），还是用 iPhone6/7/8 来举例，iPhone6/7/8 物理像素为 750px，CSS 像素为 375px，DPR 比例为 2。

假如此时 UI 设计师要给我们一张占满屏幕的图，她是按照 750px 起稿还是 375px 起稿呢？

答案是按照物理像素的 750px 起稿。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749799441841-b1cfa4bb-230f-42b6-9e22-f0e4c950bcad.png)

如上图，对于 DPR = 2 的 retina 屏（具备超高像素密度的液晶显示屏）而言，1 个位图像素对应 4 个物理像素，由于单个位图像素不可以再进一步分割，所以只能就近取色，从而导致图片模糊。

所以，对于图片高清问题，比较好的方案就是两倍图片（@2x）。

如：200 x 300 `<img />`标签，就需要提供 400 x 600 的图片，如此一来，位图像素点个数就是原来的 4 倍，在 retina 屏幕下，位图像素点个数就可以跟物理像素点个数形成 1:1 点比例，图片自然就清晰了。

<br/>tips
示例：

- 普通屏幕（dpr=1）：1 个 CSS 像素 = 1 个物理像素
- Retina 高分屏（dpr=2）：1 个 CSS 像素 = 2 × 2 = 4 个物理像素

也就是说，高分屏的“像素更密”，能显示得更细致。

假设我们画一个小图标，宽高都是 100px，我们只提供了 100 × 100 的图（普通图），在 dpr=2 的屏幕上会被“放大”到 200 × 200 的物理像素来显示，但图只有 100 × 100 像素的细节，系统只能拉伸插值模糊处理。

如果我们提供了 200 × 200 的图（2 倍图），在 dpr=2 的屏幕上，正好 1 图像像素 = 1 物理像素，系统不需要做拉伸、不插值，每一个像素都清晰对齐。

一个更加形象的例子：

你画了一幅 10 × 10 的画（低分辨率），拿放大镜看时会觉得模糊，因为你看到的是“放大的粗糙笔触”，如果你一开始画的是 20 × 20（2 倍精度），放大后就会更清晰！

<br/>

如果是普通屏幕下，也用了两倍图会怎么样呢？

很明显，在普通屏幕下，200 × 300 `<img />`标签，所对应的物理像素个数就是 200 × 300 个，而两倍图片的位图像素个数则是 200 × 300 × 4，所以就出现 1 个物理像素点对应 4 个位图像素点，所以它的取色也只能通过一定的算法（显示结果就是一张只有原图像素总数四分之一，我们称这个过程叫做 downsampling），肉眼看上去虽然图片不会模糊，但是会觉得图片缺少一些锐利度，或者是有点色差（但还是可以接受的）。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749800248023-2c70152b-897a-4ac7-9a53-6448c2443469.png)

明白了这个点之后，接下来我们来看看基于 DPR 的缩放适配方式，其原理就是将 CSS 像素缩放成和设备像素一样大的尺寸。

因为在实际开发中，设计者为了页面的高清，都会采用物理像素的值来进行设计。例如 iPhone6/7/8 的设备宽度为 375px，我们将其缩放为 750px。

常见的设计稿尺寸有：640 x 960、640 x 1136、750 x 1134。

对应的代码：

```js
(function () {
  var meta = document.querySelector('meta[name="viewport"]');
  // window.devicePixelRatio 获取 DPR 的值
  // 以 iPhone 6/7/8 为例
  // 750px * 缩放值 = 375px => 缩放值 = 375px/750px => 缩放值 = 1/DPR
  var scale = 1 / window.devicePixelRatio;

  if (!meta) {
    //这个条件成立说明用户没有写meta标签，我需要创建一个
    meta = document.createElement('meta');
    meta.name = 'viewport';
    meta.content = 'width=device-width,initial-scale=' + scale + ',user-scalable=no,minimum-scale=' + scale + ',maximum-scale=' + scale + '';
    document.head.appendChild(meta);
  } else {
    meta.setAttribute('content', 'width=device-width,initial-scale=' + scale + ',user-scalable=no,minimum-scale=' + scale + ',maximum-scale=' + scale + '');
  }
})();

```

```html
  <div></div>
```

按照 DPR 缩放为 700px 后，反而占不满了，因为我们给的宽度为 375px，因此只占了一半。

那么这种缩放的意义是什么呢？

实际上这种方式最大的意义就是开发者和设计者的像素都是统一的，因为设计者是按照 750px 来设计的（iPhone 6/7/8 为例），那么我们前端在量图的时候，也是以 750px 为基准。通过 DPR 缩放，我们量出来是多少，在写代码时就可以设置多少。

但是这种方案好像并没有解决适配的问题，假设设计稿给的是 750px 像素，我测量出来也的确是 750px，但是如果此时我将宽度设置为 750px，只能保证在 iPhone 6/7/8 中没有问题，如果换成 iPhone 6/7/8 Plus，仍然存在适配问题，那么怎么解决呢？

此时就需要我们使用 rem 适配了。

## 🔢 rem 适配
rem是什么?

rem（font size of the root element）是指相对于根元素的字体大小的单位，是 CSS3 新增的一个相对单位。

例如浏览器 HTML 默认的的字体大小为 16px，所以 1rem 就等于 16px。

示例：

```html
<p>Lorem ipsum dolor sit amet.</p>
<div></div>
```

```css
:root{
  font-size: 20px;
}

p{
  font-size: 2rem;
}

div{
  width: 2rem;
  height: 2rem;
  background-color: red;
}
```

在上面的示例中，我们设置根元素的字体为 20px，之后所有的元素设置 rem 单位表示根据根元素字体大小来缩放。例如`<p>`元素的字体大小是 2rem，也就是 2 x 20px = 40px。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749800918777-f6bce323-38b8-4bde-87e7-39ff8ae9d4a6.png)

而下面的 div 并没有设置字体大小，在设置宽度时也使用的是 rem，2rem 仍然等于 2 x 20px = 40px。

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749800936451-fbb7c3c3-c9dd-4c68-a045-70c491e9c291.png)

接下来我们来看一下 rem 实现适配的原理。

rem 适配的原理，就是把所有设备都分成若干份，再计算元素宽度所占的份数。

举个例子：iPhone5 和 iPhone6 对应的屏幕宽度是 320px 和 375px，现在我们将其分割为 100 份，那么每一份就是 3.2px 和 3.75px。看到没，不同的设备宽度，对应每一列的宽度就不一样，之后我们设置元素宽度的时候，以列为媒介即可。

比如同样一个`<div>`，我们设置它的宽度为 10 列，那么在 iPhone5 中这个`<div>`的宽度就是 32px，在 iPhone6 中这个`<div>`的宽度就是 37.5px。通过这种方式就实现了不同设备宽度，一个元素的大小可以等比例的缩放。

但是我们从 UI 设计稿出量出的尺寸都是像素，例如 100px 那么如何知道是多少列呢？

这时就需要一个转化了，我们需要算出测量出的宽度在总宽度中究竟占几列。

假如设计稿是按照 750px 设计的，我们测量出来的是 100px，那么换算成设备像素就是 50px。而一列的宽度我们是知道的，因此 50 / 3.73 约等于 13.33 列，后面设置盒子宽度的时候，就可以设置 13.33 * 一列的宽度。

再举一个例子：

```latex
iPhone5 320px
iPhone6 375px
现在设计师按照 750px 起稿，有一个元素，我们测量出来是 375px（物理像素）
换算成设备宽度就是 375/2 = 187.5
接下来计算列数：187.5/3.75 = 50
之后，我们只需要设置该元素的宽度为 50 * 一列宽度即可
在 iPhone5 中：50 * 3.2 = 160
在 iPhone6 中：50 * 3.75 = 187.5
```

而这个一列的宽度，实际上就是 rem。也就是说 rem 的适配方式，就是根据屏幕的宽度配合列数算出一列的宽度，之后设置 HTML 文档根元素的`font-size`为此宽度即可。

下面是基于此适配原理的一种实现方案：

```js
(function () {
  var html = document.documentElement; // HTML 根元素
  var width = html.clientWidth; // CSS 像素(设备宽度)
  html.style.fontSize = width / 16 + 'px'; // 把屏幕分成了 16 列
})();
```

这种方案虽然是按照我们上面讲的，将屏幕划分为 16 列，然后将根字体大小设置了每一列的宽度，例如：

```html
<body>
  <!-- 假设测量出来为 375px，换算为设备宽度为 187.5px
  然后计算出占用多少列 187.5/23.4375 = 8 -->
  <div></div>
</body>
```

设置`<html>`的`font-size`属性：

```js
(function () {
  var html = document.documentElement; // HTML 根元素
  var width = html.clientWidth; // CSS 像素(设备宽度)
  html.style.fontSize = width / 16 + 'px'; // 把屏幕分成了 16 列
  // 每一列的宽度为 23.4375
  // 因此设置根元素的字体大小为 23.4375px
})();
```

```css
* {
  margin: 0;
  padding: 0;
}
div {
  width: 8rem;
  height: 8rem;
  background-color: red;
}
```

效果如下：

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749802705116-ebe931bc-aac3-4a10-9bfe-6ba93087e14a.png)但是上面的实现方案比较麻烦的是我们在测量设计稿后要将设计稿上的宽度转为列数。

目前一种比较流行的方式如下：

```js
(function (doc, win, designWidth) {
  var html = doc.documentElement;

  function refreshRem() {
    var clientWidth = html.clientWidth;
    if (clientWidth >= designWidth) {
      // 如果设备宽度都大于设计稿了，那么测量出来是多少就是多少
      html.style.fontSize = '100px';
    } else {
      // 计算出比例
      // 拿 iPhone6 为例，375/750=0.5
      // 相当于每一列的宽度为 0.5px，分成了 750 列
      // 但是浏览器是不允许这么小的字体大小的，因此乘上一个 100
      // 变成每一列的宽度为 50px
      // 之后在将设计稿尺寸转换为列数时，也不需要繁杂的计算
      // 假设设计稿量出来为 375px => 187.5(CSS像素) => 187.5/50(每一列宽度) = 3.75(所占列数)
      html.style.fontSize = 100 * (clientWidth / designWidth) + 'px';
    }
  };

  doc.addEventListener('DOMContentLoaded', refreshRem);
})(document, window, 750);

```

上面这种方案，最方便的便是设计稿量出来的尺寸和列数之间的转换关系，只需要将量出来的尺寸小数点往前移动两位即可。

或者使用开源库`lib-flexible`来动态计算`font-size`的大小：

[GitHub - amfe/lib-flexible: 可伸缩布局方案](https://github.com/amfe/lib-flexible)

## 🔢 vw、vh 适配
CSS3 除了带来 rem 单位，还带来了 viewport 相关的 4 个单位，分别是 vw、vh、vmin 和 vmax。

- vw 是 Viewport's width 的简写，1vw 等于`window.innerWidth`的 1%；
- vh 和 vw 类似，是 Viewport's height 的简写，1vh 等于`window.innerHeihgt`的 1%；
- vmin 的值是当前 vw 和 vh 中较小的值；
- vmax 的值是当前 vw 和 vh 中较大的值；

图示如下：

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749803005304-2b7ea4a7-daed-4507-b36c-dcac2c94e27f.png)

有没有发现 vw 就相当于把屏幕划分为了 100 列，1vw 就是 1列。

那么按照 iPhone6/7/8 设备宽度为 375px，因此 1vw 就是 3.75px，而根据我们上面的公式：

```js
html.style.fontSize = 100 * (clientWidth / designWidth) + 'px';
```

将元素的字体大小设置为 50px，此时和设计稿测量出来的尺寸转换会非常的和谐，只需要小数点往前移动 2 位即可。因此我们需要计算 50px 对应多少 vw。

由于 1vw 对应的宽度为 3.75px，所以我们可以很轻松的计算出 50/3.75 = 13.33333333vw。

```html
<body>
    <div></div>
</body>

```

```css
* {
  margin: 0;
  padding: 0;
}

:root{
  font-size: 13.33333333vw;
}

div {
  width: 3.75rem;
  height: 3.75rem;
  background-color: red;
}
```

效果如下：

![](/img/user/%F0%9F%94%B5%20%E4%BB%A3%E7%A0%81%E5%BC%80%E5%8F%91/Web%20%E5%89%8D%E7%AB%AF/0%20%E5%89%8D%E7%AB%AF%E5%9F%BA%E7%A1%80/01%20CSS3/_assets/1749803246992-9d7960d2-4bb6-424e-a44f-33db92d3fe99.png)

可以看到，使用 vw 的一个最大优点就是不需要再使用前面那一大段 JS 来做处理了，因为分列的工作 vw 已经帮我们做了。唯一需要做的就是计算根元素字体应该设置多少 vw，之后从测量稿量出来的尺寸仍然是小数点前移 2 位即可。

## 🔢 1px 问题
在前端还原设计稿中经常会碰到一个问题，那就是 1px 像素问题。

移动端 1px 像素问题是指在高分辨率（高 DPR）的屏幕下，CSS 设置 1px 实际显示的要比预期看起来更粗。

我们在上面介绍 DPR 概念的时候就说了，CSS 单位是一个抽象的单位，和设备像素并不是 1:1 的关系，可能是 1:2 甚至是 1:3，所以设置 1px 时看起来会更粗一些。

对于这个问题，一般会使用下面的几种方案：

1、使用`transform: scale()`缩放。

```html
<div class="border"></div>
```

```css
.border {
  position: relative;
  height: 1px;
  background: #ccc;
  transform: scaleY(0.5); /* DPR = 2 时用 0.5，需要动态调整 */
  transform-origin: 0 0;
}
```

2、使用`box-shadow`模拟，该属性不会被 DPR 拉伸。

```css
.line {
  position: relative;
  height: 0; /* 不占空间 */
  box-shadow: 0 1px 0 #ccc; /* 上阴影当作 1px 下边线 */
}
```

> 为什么`box-shadow`是使用设备像素渲染？而`border`使用 CSS 像素渲染？
>
> 因为`boder`属于盒子模型的一部分，而`box-shadow`属于视觉装饰属性。
>

3、使用`border-image`或者`background-image`。

```css
.line {
  border-width: 0 0 1px 0;
  border-image: url(linenew.png) 0 0 2 0 stretch;
}
```

使用这种办法时需注意：

- 只在底部设置边框；
- 使用的图像 linenew.png 假定为 2px 高高度；
- 图像顶部 1px 是透明的，底部 1px 包含实际边框颜色；

4、rem 缩放。

